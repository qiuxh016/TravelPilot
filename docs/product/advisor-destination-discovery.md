# AI 旅行顾问：未定目的地探索设计

## 验收发现

顾问当前可以从用户明确提到的城市/地点开始搜索；未填写目的地时，用户可在填写出发地、日期和受支持的兴趣偏好后触发首版城市比较。系统从六个固定城市中，以高德实时 POI 搜索结果作证据，最多给出三个候选。候选只说明检索到的偏好相关地点，不推断城市交通、价格、天气或季节适宜度；模拟地图、没有证据或全量 Provider 失败时不提供城市卡片。

## 首版流程

1. 收集出发地、可旅行日期/天数、预算区间、同行人、节奏和偏好；允许用户跳过非必要项，关键条件不足时一次只追问一个问题。
2. 服务端从固定列表（成都、杭州、西安、厦门、青岛、长沙）生成有限候选；LLM 不生成城市候选，也不负责排序。
3. 对每个城市按用户明确表达的最多两类偏好调用高德 POI 搜索，最多 12 次请求；先按命中的偏好维度数、再按 Provider 返回的相关地点数排序，并展示命中数及样例 POI 名称、类别、地址和来源。未命中或查询失败的城市不进入推荐卡。
4. 展示最多 3 个城市选择卡：地点证据、偏好命中理由、来源和更新时间，并提示未核验城市间交通、预算及季节因素。
5. 用户选择城市后，城市写入会话条件；用户再搜索并选择该城市的真实 POI，生成待确认 Plan 草案。正式旅行及记忆只在用户确认后创建/改写。

## 边界

- LLM 不调用写入工具；城市候选来自可追溯数据，地图/路线/天气字段展示 Provider 状态与时间。
- 不把城市推荐文本本身当作地图核验。拒绝项先过滤，再对剩余候选排序。
- 任何推荐失败都保留对话和偏好，用户可以改填目的地或重试；不影响已存在旅行。
- 首版不做自动订票、实时价格承诺、社交热度抓取或不透明的个性画像。
- 当前固定列表和类别规则适合功能试用，不代表完整城市目录或高质量目的地排名；最多两类偏好、六城比较会消耗最多 12 次地图搜索调用。部署前须核对 AMap 对应 Web 服务配额和价格。
- 每个账户默认每 10 分钟最多比较 3 次；超出后 API 返回 429 和 `Retry-After`。Redis 键只包含服务端 HMAC 用户标识，生产环境必须设置至少 32 位 `AUTH_RATE_LIMIT_HASH_SECRET`。限额可通过 `ADVISOR_DESTINATION_LIMIT_PER_USER` 和 `ADVISOR_DESTINATION_WINDOW_SECONDS` 调整。

## 固定评测场景

| 场景 | 输入 | 期望行为 |
|---|---|---|
| 无目的地、信息不足 | “我想找自然和美食的地方” | 追问一个最高价值条件；不编造地点 |
| 有出发地和短假期 | “从上海出发，周末，喜欢自然，不要博物馆” | 城市候选展示自然类地图样本；过滤博物馆偏好；明确出发地没有参与跨城交通排序 |
| 兴趣冲突 | “想看夜生活，带小孩且希望安静” | 显示冲突并追问，不伪装成唯一正确答案 |
| Provider 部分故障 | 一个城市 POI 搜索失败 | 将该候选标成数据不足，保留其他已核验结果 |
| 无可验证候选 | 城市服务超时或候选为空 | 明示不可用并保留输入，不生成虚假地图卡/计划 |
| 用户选中城市 | 在推荐卡选择一个候选 | 再次地图搜索，生成待确认草案，用户确认前正式旅行列表不变 |

首版自动化覆盖：偏好类别必须来自支持词表、拒绝偏好会被过滤、最多两类查询、最多 12 次地图请求、最多三张城市卡、候选地点必须来自非模拟地图 Provider、用户级 Redis 限流及 429 重试时间；模拟地图直接拒绝城市推荐。真实 AMap 浏览器联调已通过；人工标注样本评估排序质量仍未完成，因此不能将推荐质量标为通过。

质量指标至少记录：条件完整率、候选城市覆盖率、地图核验成功率、拒绝偏好违规率、人工偏好排序胜率、草案硬约束违规率和 Provider 故障保留率。先以人工标注小样本验收，再决定是否扩大试用。
