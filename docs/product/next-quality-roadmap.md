# 下一阶段：攻略导入与 AI 旅行顾问质量路线

更新日期：2026-10-20  
状态：路线正在执行。阶段 0A 已完成本地实现并推送；分段失败的部分结果保留/局部重试，以及阶段 0 后续验收仍待完成。既有本地 Agent 路线的原验收结论不变。

## 目标

让用户可以把较长、格式不规则的文字或截图攻略导入 TravelPilot，得到完整、可核对、分类清楚的旅行资料；再让 Agent 理解用户的多轮表达，结合当前旅行、攻略资料、地图、路线、天气和明确同意，帮助用户完成一项有始有终的旅行任务。

“更自主”不代表替用户猜测或未经确认写入正式行程。Agent 可以自行读取上下文、选择获准工具、核对约束和提出具体方案；涉及正式行程、长期偏好记忆和其他有持续影响的数据时，仍由用户确认。

## 当前基线与已知缺口

- 文本导入通过 `apps/api/src/travelpilot_api/api/v1/content.py` 直接调用 `extract_places()`；没有独立的预解析器。图片先经本地 OCR，再把识别文本送入同一流程。
- `ContentCreate` 接受最多 20,000 字符，但 `packages/core/src/travelpilot_core/agents/extraction.py` 当前只把前 8,000 字符放入模型请求，长于 8,000 字符时会静默丢掉尾部。
- 解析结果使用地点和攻略事实 JSON Schema，事实包含类型、正文、原文证据、关联地点和置信度。一次生成可能被 completion token 上限截断；2026-10-20 的实测响应达到 1,200 输出 token，返回 3,106 字符但 JSON 未闭合。
- 导入页已展示地点候选、事实分类、置信度和原文证据；用户可确认地点并选择把事实写入地点备注。事实未被地图或官方来源核验，导入本身不会自动变成预约或正式行程。
- Skill 是受版本控制的静态指导，不会从私人导入内容自行学习。账户偏好记忆有显式开关和确认接口；攻略中的建议不等于用户本人的偏好，不能直接成为长期记忆。
- Advisor 已有受约束 Runtime、工具、追问、完整性检查、路线/天气证据、差异和确认工作台，以及本地 18 场景服务回归。开放式问题理解、短回复消歧、简洁输出和跨任务体验仍需针对真实用户输入改进。

### 执行记录：阶段 0A（2026-10-20）

- 攻略文本现在按不超过 1,000 字符的句段切分，优先在自然边界断开；模型专用提示精简，并为每段设置最多 768 个输出 token。
- 全部输入分段解析后合并地点/事实、去重并累计 token 用量；20,000 字符上限内不会再只发送前 8,000 字符。
- 本地验证：攻略导入定向测试 **42 passed**；当前工作区 API/评测回归 **904 passed**（1 条既有 Starlette/httpx 弃用警告）；Ruff 和 Web TypeScript 检查通过。
- 没有发起真实模型请求。任一段失败时目前仍会使整次解析失败；部分结果持久化和只重试失败段留在阶段 0B。

## 设计原则

1. **不静默截断**：所有被接受的原文都必须进入解析流程，或明确告知长度限制和未处理范围。
2. **证据先行**：地点、时间、票务、餐饮、路线和住宿建议必须能回指原文；地图或天气结果单独标注 Provider、获取时间和验证状态。
3. **建议与事实分开**：攻略作者的陈述、模型推断、地图核验和官方核验使用不同标签。
4. **记忆需用户确认**：导入内容不得自动成为账户偏好；Skill 不能从单个用户的私人资料自动改写。
5. **逐步扩大 Agent 能力**：先把已支持的完整任务做稳定，再增加新工具；每种写操作都保留预览、验证、同意和可追溯记录。
6. **约束预算**：分段后模型请求数会增加；每次导入必须有明确最大分段数、单段输出上限、总 token/费用预算和失败提示。

## 阶段 0：攻略长文本可靠解析（P0）

### 工作项

- 将输入按段落、列表项、句子边界分块；长行再按标点安全切分。保留原文偏移或可验证的精确引用，保证各块覆盖原文且没有遗漏或重复。
- 让每段使用紧凑、专用于攻略导入的输出协议，减少重复字段和不必要的空字段；地点与事实分开抽取，保留时间、持续时长、顺序、票务、餐饮、住宿、路线和交通细节。
- 合并分段结果：地点按规范化名称去重，事实按类型、原文范围和内容去重；跨段引用仍能关联到同一个地点。
- 设置每段上限、最大分段数及整次导入的 token/费用预算。超过预算时显示哪些部分未处理，不把截断 JSON 当作普通服务故障，也不静默丢弃尾部。
- 明确处理整段成功、部分成功、Provider 故障、结构错误、输出截断和无可用信息等状态；部分结果可保留并标注覆盖范围，用户可以重试失败段。
- 日志只记 source id、分段数量、字符范围、finish reason、token 用量和错误类别；不记 API Key、完整提示词、用户攻略原文或模型私有推理。

### 验收

- 2 万字符以内的输入要么全部覆盖，要么返回带范围的明确失败；不得只处理前 8,000 字符却仍表示输入完整。
- 测试跨段边界的地点、时间、路线和餐饮关联；所有证据都必须是原文的精确子串。
- 模拟某一段超时、空响应、JSON 截断和重试；已成功分段不重复计费（若实现持久化分段检查点），失败段可单独重试。
- 有完整覆盖才可标记完整成功；部分覆盖需有醒目的状态和缺失范围。
- 固定成本上限测试：请求数和输出 token 不超过导入策略设定的预算。

## 阶段 1：结构化攻略资料与确认体验（P0）

### 工作项

- 将事实视图整理为「游览与时间 / 票务与开放时间 / 餐饮 / 交通与路线 / 住宿 / 其他提醒」分类卡片；每张卡显示原文证据、置信度、关联地点和来源状态。
- 用户可以编辑、删除、重新关联事实；地点候选匹配不确定时给出多个选择或“稍后处理”，不能自动选错地点。
- 区分攻略整体信息与地点专属信息。只有明确关联某地点的事实才附加到其备注；整体交通、天气准备或多日路线不能误贴到每个地点。
- 加入「用户原文」「地图候选」「官方/Provider 已核验」「尚未核验」标签，避免模型复述看起来像权威事实。
- 确认后保留导入来源和原文引用；重复导入时提示重复地点/事实，提供合并或保留两条来源的选项。
- 提供一个“转为行程建议”入口：基于已确认地点和事实产生候选时间线；明确标注未核验营业时间及交通假设，用户确认后才写入行程。

### 验收

- 地点、餐饮、住宿、时间、路线和交通分别正确分类；错误类别可以在确认前修正。
- 事实只关联到相符地点；无法关联的内容保留在旅行级攻略笔记中。
- 用户确认地点后不会自动确认时间、预约、购票或住宿预订。
- 桌面与移动端都可以查看长攻略的分组结果、证据和未核验状态；没有横向溢出或被对话/弹窗遮挡。

## 阶段 2：Skill 与个性化记忆的安全复用（P1）

### 工作项

- 先把 `content-import` Skill 当成可测试、版本固定的解析规约：增加适用范围、输出约束、反例和版本变更记录。
- 用冻结的攻略集对 Skill 版本做离线比较，评估地点精确率/召回率、事实覆盖率、分类准确率、证据有效率和 token 成本；不以单个用户样本自动改 Skill。
- 识别可选的“可能适合保存为未来偏好”候选，例如用户反复明确写出的预算、节奏或饮食限制；候选必须来自用户本人明确表达，而不是攻略作者建议、餐厅名单或模型臆测。
- 只有在用户开启偏好记忆并单独确认后，才写入账户记忆；显示来源、作用范围、置信度和编辑/删除入口。旅行特定偏好默认仅对该旅行有效。
- Advisor 使用记忆前显示简短说明，并允许本次忽略；记忆检索按当前任务取少量相关项，避免把无关偏好塞入每轮提示。

### 验收

- Skill 变更必须有版本号、固定数据集比较结果和回退办法。
- 未经确认的导入内容不会写进账户记忆；关闭记忆时不创建或读取长期偏好。
- 用户可以查看、改写、禁用和删除记忆；导出与账户删除语义保持一致。
- 不从照片、社交内容或游记文本推断敏感情绪、健康、政治或其他敏感特征。

## 阶段 3：Agent 对话与用户参与（P1）

### 工作项

- 优化回答结构：先给结论或当前进度，再给 1–3 个关键理由和可执行下一步；详细来源、路线和长说明折叠展示。避免模型重复复述用户刚确认的信息。
- 为明确的待决问题提供结构化选项卡。例如时间确认显示已推导出的 A/B 方案、`其他时间` 和 `稍后决定`；用户选择可直接写为结构化答案，不要求重新组织自然语言。
- 为“这个/第二个/就按刚才说的”等短回复建立待决问题上下文和引用目标；状态过期或存在多个可能解释时先澄清，不能把模糊回复当作正式授权。
- 将当前旅行、用户已确认地点、日期、预算、节奏、已导入攻略事实、计划版本和未解决问题整理成有来源的上下文快照；每次写入前检查快照是否过期。
- 完整性审查覆盖游览、用餐、住宿、交通、休息/空档、预算、营业时间和天气准备。只对适用项主动提问，并提供“帮我推荐 / 用已导入攻略 / 稍后 / 不需要”等快捷决定。
- 天气可用时生成带预报时间和来源的穿衣、雨具、室内替代建议；不可用时明确说明，不能编造预报。
- Agent 根据工具观察决定下一步：缺地点才搜地点，时间信息缺失才问时间，路线无效才重查或解释限制；记录用户可理解的行动状态，不暴露内部推理。
- 对行程编辑展示地点、日期、时间、交通和餐饮差异；用户确认后直接应用到正式旅行，并在工作台显示新版本和撤销/再调整入口。确认前不写正式行程。
- 只增加有数据支持的工具能力；订票、付款、商家联络、社交发布等继续排除在自主执行范围之外。

### 验收

- 冻结多轮场景覆盖自然语言、错别字/口语、省略回复、话题承接、用户改口和上下文变化；Agent 能继续正确问题而不要求用户重复填资料。
- 选择卡的结构化值与自由文本等价进入同一任务状态；模糊输入触发澄清，不发生错误改计划。
- 开放咨询、攻略导入、推荐地点、餐饮、住宿、路线天气、日程检查和确认写入均可在一个对话任务中完成或给出明确边界。
- 所有正式行程写入都经过约束验证与用户确认；冲突、过期、无 Provider 证据和失败恢复有清楚提示。
- 记录并评估回复长度、有效追问率、重复问题率、任务完成率、错误工具调用、约束违规和用户修改/撤销情况。

## 阶段 4：可视化与持续评测（P1）

### 可视化交付

- 攻略导入显示分段处理进度、地点/事实计数、覆盖范围和失败段；完成后按分类呈现地点与事实，不展示无关的全量 JSON。
- Agent 工作台显示「正在理解 / 查询地图与路线 / 核对天气和约束 / 等待你选择 / 已更新」状态；工具来源、时间和核验状态可展开查看。
- 计划视图将游览、餐饮、住宿、出行和自由时间分泳道或使用清晰图标，未确定时间显示为空缺，不用虚构默认值填满。
- 选项卡说明每个选项会改变什么；提供“保留当前计划”“稍后”和“撤销/重新调整”。

### 评测与发布门槛

- 建立冻结数据集：短文本、长攻略、多日混排、无标题散文、表情/列表、OCR 错字、跨行时间、同名地点、无地图结果、部分 Provider 失败和 2 万字符边界。
- 对导入计算地点精确率/召回率、类型准确率、事实覆盖率、时间抽取准确率、地点关联准确率、证据精确率、分段完整率、平均请求数和 token 成本。
- 对 Agent 评测短回复承接、追问质量、吃住行游览覆盖、天气准备建议的来源正确性、工具选择、验证与恢复、计划变更质量、确认安全和回复可读性。
- 对比现有单次抽取/现有顾问作为基线，与分段导入、结构化交互和验证恢复版本分别消融；合成数据、模型桩、真实模型与真实 Provider 结果分开报告。
- 设定固定的本地回归门槛后，再开展少量真实模型回归；任何真实 API 调用单独设预算、记录调用数/token、避免写入正式旅行数据。

### 退出标准

- 所有冻结攻略样例都无静默丢段；有效证据均可在原文定位；失败可以解释并局部重试。
- 地点和事实分类达到冻结集预先定义的准确率门槛；门槛和评分规则须在测试前写定，不能看结果后修改。
- Agent 任务成功率提升时，硬约束违规和未确认写入仍为 0；回复长度及无效追问有可量化改善。
- 关键桌面/移动端流程通过浏览器验收，类型检查、API 回归和安全隔离测试通过。

## 执行顺序与粗略投入

| 阶段 | 交付重点 | 粗略投入 | 依赖 |
|---|---|---:|---|
| 0 | 分段抽取、合并、长度/费用边界、故障态 | 3–5 工程日 | 无 |
| 1 | 分类事实确认与导入可视化 | 3–5 工程日 | 阶段 0 的稳定输出协议 |

合计约 16–27 工程日，按一人开发约 4–6 周估算；这是实现工作量估计，不包含等待用户反馈、真实模型额度审批或外部 Provider 故障处理。每阶段先完成本地测试与可审查变更，再决定是否推送。

## 明确不纳入本轮

- Multi-Agent 编排、Skill 自动自我修改、用用户私有攻略训练/改写通用 Skill。
- 通过抓取受限社交平台链接来绕过访问限制；本轮保证粘贴文本与本地图片 OCR，链接导入需另做平台/许可/可靠性评估。
- 自动订票、付款、预约、酒店下单、自动发布动态或联系商家。
- 以“补满日程”为目标强行塞入景点；空档可由用户保留。
- 未标注来源的天气、营业时间、价格、热度或交通信息。
