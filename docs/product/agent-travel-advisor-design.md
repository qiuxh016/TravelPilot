# Agent 旅行顾问：功能与交互设计

状态（2026-10-19）：顾问现已超出最初的地点抽取原型，提供多轮受约束 Agent 工作流：模型可在服务器批准的工具和阶段中决定下一步或追问；服务端负责参数/证据核验、约束检查和有限的检查点恢复，且确认前不写正式行程。用户可从自由探索或已有旅行开始，搜索目的地/景点、餐饮和住宿，查看天气与出行建议、查询旅行内已保存地点间路线、把已选地点生成待确认排程草案，并在确认后写入 Trip/Wishlist/Plan。已有旅行上下文和已确认记忆可供顾问使用；对话可删除。实际可用范围仍由 Provider 配置、模型能力和已实现工具共同限定，不能称为可独立处理任意旅行问题的通用 Agent。

### 当前实现边界（2026-10-19）

- 已实现：账户隔离的顾问会话/消息；本人 Trip/Wishlist/当前 Plan 和已确认旅行记忆上下文；目的地探索及地图核验候选；景点、餐饮、住宿分类搜索；当前预报范围内带日期和来源的天气准备建议；路线/天气/排程等受限阶段组合；多轮必要信息追问；候选选择、日期时间输入、约束验证、PlanDiff、确认写入；取消/重试、部分跨进程检查点恢复和会话删除。混合场景的自动化产品验收覆盖 16 条本地旅程。
- 模型不可用时会依据已验证旅行事实使用有界的规则式回复；通用建议、实时 POI/天气/路线事实的可信度不同，界面与回复需保留来源和模拟/不可用标记。没有可靠 Provider 证据时不把候选、路线或天气描述成已核实事实。
- Agent 仍是**受约束的自主任务切片**：共享 Runtime 执行批准的阶段，模型可在有限观察和动作集合中选择/追问；服务器确定可用权限与执行参数，写入必须经过草案和用户确认。开放式咨询仍有独立的只读回复路径，复杂任意旅行任务尚不能自主拆解成任意工具链；检查点也不恢复任意中间推理或所有工具结果。
- 范围外/未接入：城际铁路与航班搜索、多段交通优化、酒店/餐厅/门票代订与支付、实时库存/价格承诺、全网社交平台内容抓取。路线查询当前绑定本人旅行的已保存地点；真实地图、天气功能取决于 Provider 配置及其覆盖/配额，Fake Provider 结果明确为模拟。营业时间、预算、开放状态等缺少可靠结构化数据时只作为待核验项，不作确定承诺。

## 1. 目标和边界

让不熟悉目的地的用户可以从“我还没想好去哪”开始，通过对话逐步澄清需求、比较目的地、挑选吃住玩地点、迭代每日安排，并在用户确认后将结果加入 TravelPilot 的旅行和计划中。

Agent 是旅行顾问和规划工作台，不是自动订购代理：

- 可以理解自然语言、追问必要条件、推荐目的地/地点、编排候选行程并说明取舍。
- 地点、营业时间、交通、天气等事实须标明来源和更新时间；模型生成的描述不能伪装成已核实事实。
- Agent 输出是草案。用户明确确认后才创建 Trip、加入 Wishlist、保存计划版本或覆盖当前工作流。
- 不订票、不订房、不付款、不联系商家、不自动分享位置；酒店推荐不等同房态或价格承诺。
- 确定性后端校验日期、时长、旅行边界、开放时间和交通可达性。模型不得覆盖硬约束；无法验证的项目作为警告交给用户。
- 无模型凭据时，既有旅行管理仍可用；顾问入口显示“尚未配置”，不伪造聊天或推荐结果。

## 2. 入口和使用模式

新增全局入口“AI 旅行顾问”，桌面和移动端都直接可见。建议主路由为 `/advisor`，支持可选 `tripId` 上下文；从旅行页进入时自动绑定当前 Trip。可为 `/trips/{tripId}/advisor` 提供指向同一工作台的入口。

工作台首屏给出三种明确起点：

1. **帮我选目的地**：用户尚未确定去哪，先收集出发地、可用日期/时长、预算、同行人和偏好，再给 3–5 个候选目的地及理由。
2. **我已经选好目的地**：创建临时规划上下文，补充旅行日期、预算、节奏、兴趣和限制；正式 Trip 在确认保存时创建。
3. **调整一趟旅行**：从已有 Trip 进入，读取该用户的旅行约束、Wishlist、当前计划及用户明确确认的旅行记忆；可以要求添加、替换、删减或放慢某些安排。

若用户没有旅行且从侧栏进入，默认打开“帮我选目的地”。已有旅行时仍由用户选择上下文，不能悄悄把另一个 Trip 的内容带入会话。

## 3. 核心对话流程

### A. 了解用户需求

顾问从自然语言提取信息，并以可编辑摘要呈现，而不是重复进行僵硬问卷。推荐收集：出发地、目的地确定程度、出行日期/天数、同行者及儿童/无障碍需求、预算区间、节奏、兴趣（自然/历史/购物/亲子等）、餐饮限制、住宿偏好、每日开始/结束时间、必须去/不想去地点。

- 已提供的信息不重复询问；不确定的字段允许跳过并标注“尚未确定”。
- 每轮对话后将关键条件显示为可移除/修改的偏好标签，用户可以直接说“预算提高一些”“不要早起”修正。
- 过敏、行动能力、饮食禁忌等约束由用户确认后才参与方案；界面可在提交前审阅这些信息。
- 对话中不得要求密码、支付卡号、证件号码等与规划无关的敏感数据。

### B. 目的地和吃住玩探索

目的地未定时，先输出少量候选卡片：适合原因、可能不适合之处、建议天数、季节/天气说明（仅有可靠数据时）、预估预算级别及信息来源。用户选择、比较或继续补充后再收窄范围。

目的地确定后，地点推荐分成“玩、吃、住”类别，卡片应包含名称、类别、地址/坐标（有数据时）、推荐理由、建议停留时间和来源状态。用户可逐项加入/排除，不能因 Agent 在文字里提到就自动写入 Wishlist。

- 地点实体优先来自地图/POI Provider 或用户输入；不存在可核验来源时标注“AI 建议，地点信息待核实”，并提供手工确认/编辑入口。
- 价格、评分、营业时间、酒店房态等动态字段，只有 Provider 返回时才展示来源和更新时间；不得让模型补造数值。
- 住宿按“区域/候选住宿 POI”建议，不提供未接入供应商的实时房价、空房和预订保证。
- 选择目的地推荐不自动创建正式 Trip；进入草案并确认保存时才创建。

### C. 生成和迭代行程草案

用户点击“生成行程草案”后，后端使用已选地点与旅行条件生成分日安排。草案显示：

- 每天的日期、地点顺序、建议到达/离开时间、停留时长；
- 地点间交通方式、预计时间/距离（若 Provider 有返回），未知路段明确标记；
- 预算/节奏/偏好匹配摘要；
- 营业时间冲突、过长交通、天气缺失、坐标不可靠、资料待核验等警告；
- 地图上的当天顺序标记和路线连接，并提供对应列表，地图不能成为唯一信息载体。

草案必须支持自然语言迭代，例如“第二天松一点”“把博物馆换成室内活动”“多安排本地菜”“保留西湖，删除购物”。每次修改后展示发生变化的天/地点及简短原因，重要约束改变时重新校验整份草案。用户可撤销最近一次修改或恢复最初方案。

地图表现按能力降级：

| 能力状态 | 草案表现 |
|---|---|
| 真实地图和路线几何可用 | 显示真实底图、POI 标记、按日路线轨迹、顺序/交通时间，并注明 Provider 和路线更新时间 |
| 只有 POI 坐标、无路线几何 | 显示地点标记和带方向的示意连线，明确标注“直线/示意路线，不代表实际道路” |
| 地图 Provider 不可用/未配置 | 保留完整逐日列表和地点坐标，显示地图未加载及重试；不阻断确认行程 |

当前 `RouteRead` 只有距离和时长，没有 polyline/geometry；真正画道路轨迹前需要为地图端补充有许可的路线几何数据和统一坐标系。不得把直线连线称为导航轨迹。

### D. 用户确认并保存

草案底部提供“保存为旅行计划”和“继续修改”。保存前显示明确摘要：将创建新 Trip 还是更新现有 Trip、将加入哪些 Wishlist 地点、将创建哪个计划版本，以及尚未核验的警告。

- **新旅行**：确认后一次性创建 Trip、确认过的地点收藏和第一版 Plan；若中途失败，显示部分保存状态和恢复操作，避免静默重复创建。
- **已有旅行**：默认把新地点加入当前 Wishlist，并以现有收藏 + 本次选择生成一个新 Plan 版本。已有计划和历史版本保留。
- 不默认从 Wishlist 删除地点。若草案不再安排某个收藏点，只在 Plan 中说明未纳入；删除收藏必须由用户另行确认。
- 保存成功后进入该 Trip 的计划页并打开新版本；展示地图/路线状态和“查看旅行概览”。
- 对重复提交使用草案 ID/幂等键，避免多次点击生成重复 Trip、地点或 Plan。

## 4. 页面结构与关键组件

`/advisor` 使用标准工作台壳层和明暗主题，桌面为“会话/历史侧栏 + 对话与草案主区”，窄屏按“对话 → 草案 → 地图”纵向排列。核心组件：

1. 顶部上下文选择器：新旅行、当前 Trip 或切换到其他自有 Trip；显示目的地和日期。
2. 空状态起点卡片：选目的地、已有目的地、继续规划旅行。
3. 对话时间线：用户消息、Agent 回复、地点卡、追问卡、行程草案卡和错误/重试状态。
4. 偏好摘要：日期、预算、节奏、兴趣和硬性限制，字段可快速编辑。
5. 草案审阅器：按天显示地点清单；可拖动排序属于后续能力，首版提供上下移和移除操作。
6. 路线地图：按日切换图层，列表与地图互相高亮；无真实路线时清楚显示示意状态。
7. 页面底部确认栏：草案变更摘要、警告数量、“继续修改”和“确认并保存”。确认栏不能遮挡路线地图或行程内容；未确认时禁用持久化写入按钮之外的隐式保存。

对话采用“旅行规划会话”术语。一个会话绑定一个用户，并可选绑定一个 Trip；历史会话仅当前用户可读。首版提供新建会话、重命名、删除和继续最近会话，不做分享/协同。

## 5. 建议状态和错误体验

覆盖 `未配置模型`、`未配置地图`、空会话、等待输入、生成中、需要用户补充、候选已返回、草案已生成、草案已修改、待确认、保存中、已保存、部分失败、上游超时/限额、Provider 无结果、路线不可用、权限拒绝和会话已删除。

- 长耗时请求提供取消或离开提示；重试前展示失败步骤，不重复此前成功的持久化副作用。
- 用户输入在请求失败后保留；模型无效 JSON 时转成可读错误并保留原消息。
- 推荐结果、天气和交通分别标注来源、更新时间或“未验证”；不可将旧缓存当当前信息。
- 确认按钮在至少一个行程日期和有效草案节点确定后启用；硬约束错误必须先修改，软警告允许用户确认接受。

## 6. 数据与 API 设计草案

现有单次接口 `POST /trips/{trip_id}/agent-plan-runs` 会立刻生成并保存 Plan，且不是多轮会话/待确认 API；不应直接复用它作为聊天保存动作。建议新增版本化接口，最终路径可随现有 API 风格定稿：

| 操作 | 建议接口 | 行为 |
|---|---|---|
| 创建会话 | `POST /api/v1/advisor/sessions` | 绑定当前 user；Trip 可选；设置目的地探索或旅行优化模式 |
| 会话列表/详情 | `GET /api/v1/advisor/sessions[/{id}]` | 只返回所属用户的会话和消息分页 |
| 发送消息 | `POST /api/v1/advisor/sessions/{id}/messages` | 追加用户消息，执行澄清/候选推荐/草案迭代，返回消息与结构化产物 |
| 获取草案 | `GET /api/v1/advisor/sessions/{id}/draft` | 返回结构化行程、地点、约束结果、路线状态和 warnings |
| 确认草案 | `POST /api/v1/advisor/sessions/{id}/confirm` | 校验草案版本后幂等写入 Trip/Wishlist/Plan，返回新资源 ID |
| 删除会话 | `DELETE /api/v1/advisor/sessions/{id}` | 删除会话消息和未确认草案；已保存 Trip/Plan 不随会话删除 |

建议持久化实体为 `AdvisorSession`、`AdvisorMessage` 和 `AdvisorDraft`（或按会话 JSONB 保存带版本的草案）。至少记录 owner、可空 trip_id、状态、消息角色/正文、结构化建议、草案版本、确认结果 ID、创建/更新时间和失败类别。未确认草案不可写入正式 Wishlist/Plan 表。对话和原始攻略属于用户内容，日志不得记录正文或模型密钥；为会话提供删除入口和明确保留政策。

消息响应优先采用结构化 payload：`assistant_text`、`intent`、`missing_fields`、`preference_summary`、`place_candidates[]`、`draft_revision`、`warnings[]`、`provider_status`。模型输出通过 Pydantic Schema 验证，未通过时不执行工具和保存动作。

## 7. 安全、所有权与可靠性

- 所有会话 CRUD 必须用 `get_current_user` 并在查询中同时按 `session_id` 和 `owner_id` 限定；可选 `trip_id` 必须验证为当前用户所有。不能只依赖前端隐藏入口或通用路径中间件。
- Agent 的每个工具只能接收服务端派生的用户/Trip scope，不接受模型指定任意用户、Trip 或资源 ID；读取 wishlist、memory、plan 前再次做所有权过滤。
- 现有 `require_request_scope` 检查 `trip_id`、Wishlist item 和内容资源，但 `AgentRunModel` 仅关联 Trip，缺少独立会话/消息 owner；新增会话后应把所有权关系作为数据模型一等字段并补越权测试。
- 所有工具调用设 allowlist、超时、输入大小和每会话步数上限；模型不能直接运行 SQL、访问任意 URL、执行支付或修改用户资料。
- 用户粘贴的攻略、网页内容和地点描述作为不可信数据，不能当系统指令；模型只输出候选操作，由后端验证并由用户确认。
- 对话/草案确认用版本号防止旧标签页覆盖新修改；确认操作幂等；上游失败时不留下半完成计划。
- 限制每用户并发会话、消息长度、请求频率、模型 token 与地图调用预算；错误向 UI 返回分类和请求 ID，不回传密钥、堆栈或供应商原始敏感内容。

## 8. API 凭据和服务端配置占位

现有 API 已有服务端 Settings 字段 `LLM_API_KEY`、`LLM_MODEL`、`LLM_BASE_URL`，默认 Base URL 指向 OpenAI-compatible `/v1`；当前没有对应前端配置项，也不应新增浏览器可见 Key。后续接入时由用户提供所用 API 的兼容协议、Base URL、模型 ID 和 Key/部署密钥，由服务端环境注入；界面只显示“已配置/未配置/调用失败”，永不回显 Key。

规划中的调用配置（暂不填值）：

```dotenv
LLM_BASE_URL=
LLM_MODEL=
LLM_API_KEY=
ADVISOR_ENABLED=false
ADVISOR_REQUEST_TIMEOUT_SECONDS=30
ADVISOR_MAX_TURNS_PER_SESSION=
ADVISOR_MAX_OUTPUT_TOKENS=
```

前三项已对应现有 Settings；后三项是建议新增配置，需在实现前确认默认上限和关闭策略。地图 Provider 沿用现有服务端配置，真实路线几何和天气需分别完成 Provider 评估/额度/许可/署名设计后再接入。API 未配置时不阻塞其它旅行功能。

## 9. 分阶段交付与验收

### 阶段 A：可演示的 Agent 顾问 UI（模型 API 留空）— 已完成初版

- 已建立全局入口、三种起点、偏好摘要、消息/候选卡片、草案审阅、地图能力降级和确认前摘要。
- 使用明确标记的静态演示数据；演示数据不能保存成用户正式 Trip 或伪装真实推荐。
- 初版验收：浅色默认、深色完整；桌面/手机入口可见；fixture 标识明确；仅登录状态检查触发 `/auth/me`，顾问页面不请求模型、地图或旅行写入 API。交互已用 Playwright 在桌面与窄屏验证。

### 阶段 B：会话与草案服务 — 首版已完成，编辑能力继续迭代

- 已实现 owner-scoped 会话、消息和版本化草案 API；有会话删除、幂等确认、当前计划版本冲突检查和账户导出/删除覆盖。
- 现阶段以确定性规则驱动已有旅行编辑，模型 Adapter 可关闭；地点信息仍须由地图 Provider 核验。
- 已验证：两个账户不能读取、更新、确认或删除对方会话/草案；草案确认前不写入 Trip/Plan；旧计划保留；过期草案拒绝确认；确认重试不会重复创建记录。

### 阶段 C：接入用户提供的模型 API

- API 兼容性检查、服务端密钥、超时/限额、结构化输出、失败回退和隐私告知。
- 验收：无 Key、错误 Key、超时、格式错误、限额和正常建议均有明确状态；模型无权绕过硬约束或直接持久化。

### 阶段 D：真实地点、路线和天气

- POI 结果校验、真实路线 geometry/坐标系和天气 Provider 接入；显示 Provider、更新时间和覆盖边界。
- 验收：真实路线可画在同坐标系底图上；无 geometry 时降级示意线；地图/天气中断不丢草案或已保存计划。

## 10. 本功能明确不做

- 群聊、旅行分享、共同编辑、公开 Agent 商店或跨用户记忆。
- 代订机票/酒店/餐厅、支付、优惠券、商家联系和库存承诺。
- 无人工确认的正式 Trip/Wishlist/Plan 写入、自动删除收藏或自动接受实时事件重规划。
- 把模型常识当实时事实，或把示意连线称为实际道路导航。
- 用前端直连用户模型 API Key；密钥只由服务端读取。
