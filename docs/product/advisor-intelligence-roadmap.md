## 当前判断

本机项目根目录 `.env` 配置的是 DeepSeek OpenAI 兼容接口，模型名为 `deepseek-flash`，并且存在 API Key 配置。顾问代码通过 `LLM_BASE_URL`、`LLM_MODEL` 和 `LLM_API_KEY` 调用它。运行中的 API 进程是否加载了这份配置，仍取决于启动进程时的工作目录和环境变量；不能仅凭文件配置断言正在运行的服务已使用该模型。

顾问目前并非每轮都由模型完整思考和回答：

- 模型主要用于抽取意图、地点和搜索词，以及基于服务端提供的事实组织简短回复。
- 开放探索且尚无目的地时，部分回复走固定模板；当前回复生成器只接收压缩后的旅行上下文，输出上限较小，并被要求不超出给定事实。
- 已有旅行的排程、地图候选搜索和按旅行日期的天气查询进入受约束 Agent Loop；意图分类、查询许可范围、完整性检查和硬约束仍由服务端确定性逻辑把关。
- 草案天气卡片会按预报数据给出带伞、分层穿衣、高温防晒和室内备选提示；直接天气咨询也会显示预报日期、来源与更新时间。
- 推荐结果已支持餐饮、住宿和景点分类，也能手动确认时间；候选与对话、地图、选择汇总及下一步行动之间的关系仍不够直观。

因此，当前体验的主要限制不只是模型本身，而是**对话理解、工具决策、旅行完整性检查、天气解释和候选操作没有组成一条连贯的用户流程**。

## 产品目标：广覆盖、可验证的旅行 Agent

“能独立处理任意旅行问题”在产品上定义为：覆盖旅行全流程中明确支持的任务类型；Agent 能根据当前旅行状态和工具观察自主推进多步任务，在信息不足时集中追问，在工具失败或证据不足时说明限制，并给出可检查的结果。它不承诺回答任意领域问题，也不允许模型绕开服务端权限或验证。

覆盖的用户任务分为六类：

1. **发现与决策**：不知道去哪、比较目的地、按时间/预算/偏好缩小选择；缺少关键条件时先问少量高价值问题，也能在信息很少时给出带假设标注的初步选项。
2. **行前规划**：把已收藏地点、攻略、偏好和出行日期整理成多日方案；区别景点、用餐、住宿和交通；检查路线、时间、营业信息与预算限制。
3. **行前准备**：按真实天气预报、地点与行程日期给出衣物、雨具、交通准备建议；说明预报覆盖范围和更新时间。
4. **途中调整**：处理天气变化、延误、临时闭馆、用户疲劳或新增兴趣；读取当前计划，只提出必要的局部变更，并保留固定预约。
5. **信息补充与导入**：从用户提供的文本、图片或可访问链接提取地点和线索；把提取结果标为待核验，核实后才用于路线和计划。
6. **旅行记录与回顾**：按用户明确授权使用照片、文字和地点生成记录/文案建议；记忆偏好需用户确认、可查看、修改、删除或关闭。

Agent 的标准工作循环：读取任务与旅行状态 → 找出关键未知 → 选择一个受限动作（追问、调用只读工具、分析、形成方案、结束）→ 检查工具结果和证据 → 验证硬约束 → 更新任务状态 → 继续、请用户决定或给出结果。每一步都记录动作、依据、来源和失败原因；达到步数、时间或 token 上限时要安全停止并说明进度。

Agent 可以自主执行范围内的只读查询和分析；新增/删除地点、调整已确认安排、保存正式计划，以及任何外部副作用，必须展示影响和差异并取得用户明确确认。服务端负责权限、工具参数边界、事实校验、计划约束、版本冲突和写入；模型负责理解、选择下一步和解释结果。

## 下一阶段：从专用切片扩展到通用旅行任务

### 阶段 A：统一多轮任务状态和决策循环

**状态：共享阶段运行时和安全重试已实现，通用自主任务覆盖仍部分完成。** 排程、地点搜索、日期天气和已保存地点间驾车/步行/城市公共交通查询均有受约束循环；追问具备稳定任务 ID、有限回答历史和旅行上下文版本校验。同一消息可能已在服务端提交但客户端未收到响应时，前端重试会复用幂等键。循环状态写入独立事务的运行事件；带幂等键的重试可恢复已经验证的路线矩阵、日期天气、普通地点搜索、目的地城市/兴趣搜索结果和两地路线几何。搜索/天气/路线/目的地发现以及排程的路线/草案决策会保存待执行动作的不可逆哈希引用；重试仅在批准查询、观察、决策编号、账户/会话/上下文和工具权限均匹配时重放动作。地图/天气/路线快照有 owner、会话、任务、上下文/查询范围、Provider 来源和 10 分钟新鲜度约束；敏感原文不进快照，快照不通过进度 API 返回。旅行顾问主回合的搜索/天气、路线和排程阶段现由单个 `AdvisorTurnExecutor.execute_adaptive` 驱动；目的地发现外围阶段也遵循共享生命周期，内部城市/兴趣搜索仍由专用受限循环选择下一步。PostgreSQL/API 路由故障注入通过同一幂等键跨新数据库会话恢复；同幂等任务重试可查看上一阶段序号、选择历史和中断阶段，但必须重建当前事实、重验领域证据后再继续。我们不序列化任意模型文本作为可信状态。多任务端到端 Agent 质量评测和更多进程/并发故障注入仍未完成。当前已实现的是每轮/会话输出 token 上限，不是供应商美元成本的硬限额。

- 定义 `AdvisorTask` 状态：用户目标、任务类别、旅行快照版本、已确认事实、待确认信息、工具观察、候选方案、风险/约束、审批状态、下一步和截止预算。
- 统一结构化动作：`ASK_USER`、`CALL_TOOL`、`ANALYZE`、`PROPOSE_CHANGE`、`FINISH`；工具只从服务端按任务授予的 allowlist 中选取。
- 让每次决策都读取当前观察；不能把固定 Python 步骤包装成“自主决策”。避免重复查询，路线/天气观察过期时再刷新。
- 把等待用户回答、进程重启、工具超时和重试纳入可恢复状态；幂等标识避免重复写入或重复创建草案。
- 约束最大步骤、单工具超时、重试次数、单轮和会话累计 token/成本；预算耗尽时保留进度并给出继续选项。

**退出条件：** 同一目标能在至少三轮交互中保留状态；工具结果会改变后续动作；注入超时、无效结果、上下文过期时能安全继续、追问或停止；自动化测试证明不同状态对应不同预期决策。

### 阶段 B：按用户任务开放旅行工具

**状态：部分能力已有；统一任务覆盖待做。** 先补齐现有地图、天气、旅行上下文和计划工具的统一协议，再按用户结果增量增加工具。对明确的酒店/车票/机票/门票/餐位代订请求，Advisor 现在会在地图、路线和排程工具执行前停止，给出不支持外部下单的明确说明；普通住宿、餐饮和景点搜索保持可用。该边界已由 API 回归和桌面/移动端完整 Advisor E2E 验证。

- 目的地发现：目的地候选、比较维度、地图检索。热度/评分必须有来源；无法确认时不得描述为实时榜单。
- 行程规划：读取收藏/计划、距离矩阵、营业时间（数据可用时）、确定性排程、PlanDiff 与约束报告。
- 吃住行：分类搜索餐饮/住宿/交通信息；不跨类别推荐；价格、可订状态、班次等动态数据必须来自实时可验证 Provider，否则标注未核实。
- 天气与准备：按旅行日期查询预报、解释预报时间范围、生成穿衣/雨具建议；超出预报范围时给季节性一般建议并清楚标示。
- 途中重规划：将天气、闭馆、延误或疲劳事件转为影响范围，优先做最小修改，保留固定/预约节点，提供无法满足约束的原因。
- 内容导入与记忆：提取结果需展示原文/图片出处、置信度和待核实地点；偏好记忆必须由用户确认并可管理。

**退出条件：** 每类任务有工具契约、失败行为、事实来源和边界用例；工具权限最小化；没有工具覆盖的请求会说明能力边界或询问用户，不编造数据。

### 阶段 C：验证器与行动审批

**状态：确认门和排程验证已有；需推广到统一任务循环。**

- 对事实回答区分“工具已验证”“用户提供”“模型一般知识”“未知”；展示必要的来源和更新时间。
- 由确定性验证器检查日期/地点一致、交通可达、时间不冲突、固定安排不变、分类正确、预算约束和数据新鲜度。
- 工具结果不合格时可换安全工具、重试一次、降级为明确标注的估算或追问；不合格证据不能静默进入正式草案。
- 写入类动作先生成预览、变更差异、约束结果和影响说明，再由用户确认；拒绝或撤销时不改正式数据。
- 明确可自主完成、需要用户决定、需要强确认、当前不支持四类动作。

**退出条件：** 多轮任务中未确认写入为零；过期草案与版本冲突被拒绝；所有副作用在 UI 预览后执行；故障恢复不损坏已有行程。

### 阶段 D：偏好记忆与个性化

**状态：记忆开关与生命周期接口已存在；顾问会话按轮刷新已确认记忆。本轮明确要求优先，硬限制冲突由服务端草案验证器把关，且匹配按类别语义分句处理。12 个合成合同案例覆盖作用域和否定边界；新的 12 案例查询策略对照在开启/关闭记忆时均为 12/12 作者标签通过、0 个显式范围违规。该评测发现并修复固定类别顺序挤掉用户明确提及的后续兴趣问题。模型仅在用户开启记忆后提出非敏感旅行偏好草案；用户审阅并选择“偏好”或“必须遵守”后才保存，来源标为 `MODEL_SUGGESTED`。真实候选相关性、个性化收益和用户效用仍待评测。**

- 将显式长期偏好与单次旅行要求分开；保存前向用户说明内容与用途。
- 记忆只作为可撤销的建议依据，不能覆盖本轮明确指令；冲突时以本轮指令为准并可询问。
- 允许查看、修改、删除、导出和关闭记忆；记录来源与更新时间，不从照片或情绪中自动推断敏感属性。
- 评测个性化收益和负迁移：比较启用/关闭偏好记忆时的约束违规、偏好匹配和用户修正量。

**退出条件：** 用户可完整控制记忆生命周期；确认记忆带来可重复的偏好匹配改善，且不增加硬约束错误。

### 阶段 E：任务工作台与用户参与

**状态：现有旅行多轮规划工作台显示运行中检查点、候选、地图和草案；追问以可见决策卡呈现，提供直接回答、取消和切换新问题入口，新消息会将聊天滚入视口。桌面 Chromium 完整流程（含任务切换）通过；先前桌面与 Pixel 7 移动端的基础追问/确认流程通过。其他任务类型的统一工作台体验仍待完成。**

- 顶部明确显示当前旅行/自由探索、任务目标和执行状态。
- 时间线展示“已了解、正在查询、需要你回答、等待确认、已完成”，工具步骤可展开查看数据来源和失败信息。
- 把追问做成可选项并允许自由输入；用户可修改 Agent 对偏好、日期和约束的理解。
- 结果区展示推荐理由、候选对比、计划差异、路线/天气依据和未解决问题；用户可以逐项采纳、跳过或编辑。
- 支持暂停/继续、重试失败步骤、撤销待确认草案和切换任务，不让用户依赖隐藏的内部状态。

**退出条件：** 用户测试能说明 Agent 正在做什么、依据是什么、还缺什么、确认后会发生什么；桌面和移动端均能完成端到端任务。

### 阶段 F：分层评测和发布门槛

**状态：已有离线对照、开放咨询与多轮动作真实模型评测，以及一条产品 API 两轮真实旅程；多任务盲评仍待做。** `advisor_multiturn_v5` 冻结了 60 项任务、129 轮对话、十个任务族，并将 `allowed_tools` 限制为当前 Advisor 已注册工具；确认提交、内容导入和个人记忆 API 标为服务端/产品流程，不再冒充模型工具。协议回放和实时动作比较可验证状态续接与首步选择，但不能代替跨任务产品质量评分。当前还缺少独立人工盲评、足够样本量和用户接受/修改率指标。

现有旅行 Advisor 浏览器端到端流程已在隔离本地栈再次通过：桌面 Chromium 与 Pixel 7 移动 Chromium 共 2/2，覆盖多轮上下文、搜索/排程/路线工具、确认门槛、过期计划、待办失效和取消待办。取消后任务状态为 `CANCELLED`，正式行程版本数未变化。该流程使用脚本模型与 Fake Maps，仅证明这一条产品路径可运行，不证明跨任务 Agent 质量。

- 建立 60–80 个冻结的多轮旅行任务，按发现决策、规划、吃住行、天气准备、途中重规划、内容导入、偏好记忆和故障恢复分层；保持隐藏扰动和无工具/失败 Provider 案例。
- 对照固定流程、Agent Loop、Agent Loop + Verifier/Recovery；同一输入状态、模型版本、工具响应与预算保持一致。先离线 Mock，再 Provider 联调，最后小预算真实模型抽样。
- 主要指标：端到端完成率、有效追问率、工具选择适应率、事实无依据率、硬约束违规率、恢复率、用户修改/接受率、耗时与 token/API 成本。

- 真实模型实验先冻结数据集和评分规则，声明最大请求数和成本上限；每个任务输出需做人工抽查，不能仅靠模型自评。

**退出条件：** 核心任务组达到预先设定的成功和安全阈值；关键失败有可复现案例；相对固定流程的收益通过同任务配对比较，而不是只报告动作匹配率。

### 推荐执行顺序

1. 先完成阶段 A，将排程、地点和天气能力接到统一可恢复循环，并扩展多轮评测；这是自主性和工程可控性的底座。
2. 再完成阶段 B 的用户任务覆盖和阶段 C 的统一验证/审批，优先跑通“发现目的地 → 选择吃住玩 → 安排路线 → 天气准备 → 确认保存”一条纵向流程。
3. 同步完成阶段 E 工作台，让用户能参与选择和纠正 Agent，而不是只看最终回答。
4. 再做阶段 D 个性化记忆；Skill 保持轻量、版本固定，仅在明确任务收益时加入，不做自我修改或迁移学习。
5. 最后按阶段 F 做受控对照和试用验收；只有预算与安全门槛通过后再扩大真实模型及外部 Provider 调用。

## 阶段 1：开放式对话与 Agent 行动路由

**状态：主要支持任务已接入共享受约束阶段执行器；通用自主 Agent 尚未完成。** 排程、地点搜索/天气、已保存地点间路线使用同一阶段状态、依赖、检查点和自适应排序机制；目的地发现复用共享阶段生命周期，但城市与兴趣搜索仍由受限领域循环负责。一般追问与工具追问保存稳定任务 ID、上下文版本、轮次和最多 6 条有界回答。重试会从持久化用户输入重建当前业务事实，只复用通过 owner、会话、任务、上下文、Provider 和时效校验的证据。它不会恢复任意模型思维或原始中间输出，也未证明任意工具链的精确续跑。因此目前只能称为多个边界明确的自主任务切片，不能称为可独立处理任意旅行问题的通用顾问。

### 工作项

1. 排程、地点搜索、日期天气、目的地发现及已保存地点间路线的受约束只读切片已实现；主顾问回合中的搜索/天气、路线、排程共用阶段执行器，目的地发现接入同一生命周期。意图模型现在可以从当前消息提出带逐字证据的景点/餐饮/住宿/天气/准备/路线/排程任务，服务端校验引用并过滤显式否定后才把它转为已批准任务；自然语言改写可因此绕过部分固定关键词触发。开放咨询的最终回复仍走独立只读合成路径，尚未成为任意多步工具规划循环；新任务字段还需真实模型格式与路由评测，并继续收敛重复服务端策略，模型不得直接控制业务写入。
2. 开放咨询允许基于通用旅行知识作一般性建议，但地图地点、营业时间、价格、天气、路线等事实必须来自工具结果或明确标成未核实，不能伪装成实时信息。
3. 在自由探索状态也启用模型回复；缺少目的地/日期/偏好时，只追问推进当前目标所需的少量信息，而不是让用户重新填写完整表单。
4. 地点搜索、天气、排程和一般模型追问保存任务 ID、原始目标、问题、上下文版本、轮次和有界答案历史；用户回答后恢复原任务，旅行上下文变化会使旧任务失效。经校验的地图、天气、路线及工具决策证据可在同幂等重试时重建；PostgreSQL 进程级故障演练目前覆盖有限任务和阶段组合。仍需扩大跨领域失败顺序覆盖，并以冻结任务集验证续接质量、有效追问和任务完成率。
5. 每轮在界面展示“正在了解 / 正在查询 / 正在核对 / 等待你选择 / 草案待确认”等状态，并提供简短行动依据。

### 验收

- 8–10 个固定开放问题覆盖“目的地不确定”“只给模糊兴趣”“问已选地点怎么安排”“询问准备事项”等场景。
- 顾问能给出有帮助的第一步，或提出一个明确且相关的追问；不能只重复让用户提供地点名称。
- 模型不可用时明确说明并提供可用的规则式后备路径。
- 不存在未确认写入；模型输出不能直接越过服务端验证或用户确认。
- 地点搜索的模型决策仅能使用服务端批准的搜索词和当前旅行城市；越界参数会被忽略并回退到安全请求。

## 阶段 2：完整旅行需求检查与可选补齐

**状态：本地主要闭环完成。** 草案会检查餐食、空档、空日、住宿、出发地和路线证据；对至少 3 个安排、跨度不少于 9 小时且没有 45 分钟显式空档的日期增加非阻断休息检查，用户可请求更轻松的待确认安排、保留现状或稍后处理。提醒有持久化的“稍后/不需要/恢复”、针对单个缺项的处理卡及草案版本冲突保护。针对餐食/活动/住宿缺项，用户可选“顾问推荐/攻略导入/稍后/这次不需要”；针对休息检查不显示无关的攻略导入入口。针对当前选中缺项只展示一个攻略导入入口，避免多个按钮打开同一导入窗口。预算、营业时间与交通方式的完整联合检查仍按现有数据能力提供，缺数据时不作确定判断。

### 工作项

1. 生成草案前后执行旅行完整性检查：交通/出发方式、住宿、每日游览、用餐、休息/自由时间、预算和硬性限制。仅在与旅行天数、时间和用户意图相关时提出检查项。
2. 每项提供清晰选择：**帮我推荐、从攻略导入、我稍后处理、不需要**。每项独立处理，避免一次弹出过多问题。
3. 推荐类别严格匹配用户意图：询问午餐只返回餐饮；找酒店只返回住宿；开放推荐才混合展示并分组。保留已有确认地点，不因搜索其他类别而意外清空。
4. 交通建议展示地点间的可核验方式、时间和来源；没有可靠路线数据时说明估算/不可用，不虚构交通方式。
5. 检查地点顺序、跨区耗时、营业时间、已锁定预约、餐食时间、过长空档和单日负荷；不可行时指出冲突并给出可选放宽项。
6. 用户选择候选并填写/确认时间后，重新生成差异草案；保留原计划，直到用户明确确认。

### 验收

- 测试至少包含一日游、多日游、无过夜、需要住宿、用户自带攻略、明确跳过餐食、交通工具未定等场景。
- 系统不会默认替用户决定未表达的日期、时间、住宿或预算。
- 餐饮/住宿查询不会混入游览景点，且各类地点在候选卡片和计划时间线上有一致标签。
- “稍后”与“不需要”不会反复打断当前会话；用户可以主动重新打开检查项。

## 阶段 3：天气建议而不只是天气数字

**状态：本地实现完成，实时覆盖范围继承天气 Provider。** 每日天气结果会附带保守的雨具、穿衣、高温提示；强降水可直接询问室内备选。无预报不生成伪造的具体天气结论。

### 工作项

1. 在每天预报卡片中加入可解释的出行提示：降水概率较高时提醒雨具；温差较大或偏冷时建议分层穿衣；高温时提醒防晒和补水。规则阈值集中配置并注明这是基于预报的通用建议。
2. 建议与天气数据绑定日期、地点、来源和更新时间；超出预报范围或接口不可用时明确标记，不继续生成看似确定的提示。
3. 结合当日户外地点和路线，提示用户可选择室内替代点；天气变化只形成待确认建议，不自动改写行程。
4. 在执行前确认 Provider 返回的数据字段及缺失处理；只有在需要风速等新字段时再扩充 Open-Meteo 请求。

### 验收

- 雨天、低温/大温差、高温、正常天气、无预报五种情况有不同且可追溯的 UI 提示。
- 文案不声称确定天气，不将天气提醒当作医疗或安全保证。
- 用户可从天气提示直接查看受影响的户外安排并选择是否询问替代方案。

## 阶段 4：重做地点推荐的可视化与操作路径

**状态：主要交互已实现；本轮端到端浏览器验收通过。** 已提供任务类别筛选、候选地图展开、选择数量分组、时间确认、天气提示和草案差异/确认入口。桌面 Chromium 与 Pixel 7 移动 Chromium 均通过现有旅行 Agent 多轮规划、轨迹展示、逐项稍后/恢复以及确认后写入验收。

### 当前体验问题

- 候选卡片、已选地点、输入日期时间和草案变更同时堆在右侧，用户难以判断当前是在浏览、选择还是编辑。
- 顾问的文字回复与候选列表没有稳定的一一对应；候选的推荐原因、数据来源、距离/交通和适合时段不够突出。
- “加入地点”后下一步不够明确，时间输入和草案生成的关系较弱；草案/差异又出现在页面更下方。

### 目标流程

1. **先选要完成的事**：游览地点 / 用餐 / 住宿 / 交通与路线 / 综合建议；自由提问保持可用。
2. **看推荐结果**：每张卡片展示名称、类别、地址、地图评分或真实来源、推荐原因、距当前路线的估算/核验信息；缺失数据不显示虚假指标。
3. **对比并选择**：按类别筛选，卡片支持查看地图位置/加入待选清单；地图和列表联动；清楚展示已选数量和类别。
4. **确认安排**：选择具体日期和时间，标出用户明确说过的值与尚待用户输入的字段；餐食时间用“午餐/晚餐”标签表达。
5. **检查并保存**：集中展示每日时间线、地图路线、吃住行缺口、天气提醒、约束警告和 PlanDiff；只保留一个明确的“确认并保存”动作。

### 验收

- 用户能清楚回答“我现在在做哪一步、选了什么、还缺什么、下一步会发生什么”。
- 推荐卡片上的类别、选中状态、日期时间和草案内容保持一致。
- 桌面和移动端均有清楚的筛选、空状态、加载状态、错误状态和返回/编辑路径。
