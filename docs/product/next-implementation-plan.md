# Archived: earlier UI-only implementation plan

> This plan predates the live map/weather integration and the multi-user product work. It is kept as historical context; the current execution roadmap is [ROADMAP.md](../../ROADMAP.md), with the Agent runtime target in [agent-runtime.md](../architecture/agent-runtime.md).

状态：计划稿，尚未开始实施。本阶段目标是在不接真实地图、天气或模型 API 的前提下，让用户能完整管理旅行、收藏地点和版本化计划。地图与天气继续使用已明确标注的本地演示数据。

## 当前基线

- 登录后工作区已统一为桌面固定侧栏、移动端两列导航；浅色默认，深色可切换并记忆选择。
- 旅行详情、地点搜索/导入、计划、事件、记忆和账户页面已经存在。
- 地图与天气目前是 UI 演示，不请求真实 Provider。
- 后端已有 Trip `PATCH/DELETE`、Wishlist `PATCH/DELETE`、计划节点 `PATCH/DELETE` 和计划版本查询能力；Web API client 和页面尚未提供完整操作入口。
- Wishlist 当前 `PATCH` 只支持优先级、兴趣分和备注；若产品需要改地点名称/地址/坐标，需另行扩充服务端 Schema 并验证坐标来源。

## 阶段 1：Trip 与 Wishlist 可维护

### 任务

1. 在 Web API client 增加 Trip 更新/删除、Wishlist 更新/删除方法，沿用统一错误处理和请求状态。
2. 在 Trip 详情提供编辑旅行表单，支持目的地、日期、预算和节奏；删除旅行需显示对象、级联后果和不可撤销确认。
3. 在 Wishlist 项目卡片提供优先级、兴趣分和备注编辑，以及移除操作；编辑失败时保留表单输入。
4. 用户加入/删除/修改地点后刷新 Wishlist、地图示意图和计划状态提示；有旧计划时提示它基于旧收藏生成，提供显眼的重新生成入口。
5. 所有资源操作继续通过带 `tripId`/资源 ID 的受保护 API；跨用户资源不可通过前端状态推断权限。

### 验收

- 用户可在旅行详情完成 Trip 修改、Wishlist 修改和删除，刷新后数据仍一致。
- 删除 Trip 前明确告知关联数据将级联删除；取消确认不产生请求。
- 修改优先级/备注后地图和地点列表显示同一份数据；删除后对应地点立即消失。
- 网络失败时显示可读错误，表单不清空；重复点击不会创建重复请求。
- 用户 A 通过 UI 不能操作用户 B 的 Trip/Wishlist；服务端 404/权限错误显示为通用无权访问提示。

## 阶段 2：计划版本与节点调整

### 任务

1. 将计划页整理为逐日时间线，显示地点、起止时间、停留时长、状态、警告和当前版本。
2. 历史版本做成可选择的列表/下拉项；选择旧版本通过既有查询接口加载，不误覆盖当前版本。
3. 加入节点编辑：日期、开始/结束时间、优先级、状态和备注；加入节点删除的二次确认。
4. 编辑/删除按现有 API 语义生成新版本；显示版本号和 `USER_EDIT` 变更记录，让用户能回看变更前后。
5. 处理冲突响应（如 409）：保留输入，指出需要调整的时间或约束，不显示成功状态。
6. 重新生成计划前说明会依据当前 Wishlist 和旅行约束生成新版本；历史版本继续可读。

### 验收

- 用户能切换任一历史版本并看到该版本对应的节点。
- 节点编辑或删除产生新版本；旧版本内容不变，变更记录可查看。
- 无节点、空计划、生成中、Provider/规划失败、约束警告均有清楚的页面状态。
- 任何编辑失败都不丢失用户输入；版本编号、计划内容和 diff 来源一致。

## 阶段 3：事件重规划可理解

### 任务

1. 事件表单中的 POI ID 改为从当前 Wishlist 选择地点，不要求用户手工复制内部 ID。
2. 对延误、天气变化、疲劳、地点取消等事件显示不同的字段、说明和校验。
3. 天气事件始终标记为“手动模拟”；不把本地天气样例自动当成事件，也不在切换天气下拉框时后台重规划。
4. 结果区按 KEEP/ADD/REMOVE/MOVE/UPDATE 分类展示，列明时间前后、原因和警告；显示新版本链接。
5. 增加运行中/超时/可重试状态；若使用异步任务，显示任务状态，不重复创建任务。

### 验收

- 用户可从当前 Wishlist 选择取消/新增/预约变化相关地点，不接触 UUID。
- 每种事件仅出现相关输入；非法时间和日期在提交前提示。
- Diff 结果可以追溯到事件和新旧计划版本；空 diff 也有明确解释。
- 重规划失败不覆盖已有计划；模拟天气不会伪装成真实天气 API 触发。

## 阶段 4：一致性、移动端与权限验收

- 核对浅色/深色在列表、表单、地图模拟、天气模拟、Diff、登录和账户页面中的对比度、焦点与禁用态。
- 移动端检查旅行表单、地点列表、时间线编辑、Diff 和主题切换，无横向溢出；主要操作不被固定导航遮挡。
- 验收加载、空数据、错误、无权限、重复提交和重试状态；危险操作均有准确确认文案。
- 覆盖账户隔离：列表只出现当前用户资源；直接访问他人 Trip、计划、Wishlist 或记忆时统一无权访问。
- 浏览器闭环：注册/登录 → 创建 Trip → 添加/编辑/删除 Wishlist → 生成计划 → 编辑节点并切换历史版本 → 模拟事件并查看 Diff → 确认记忆 → 导出/删除账户。

## 后续阶段：真实地图与天气

完成阶段 1–4 后再启动 Provider 工作：地图先定坐标体系、底图许可/额度与 Key 安全方式，再把地图示意图替换为真实视图；天气先定数据服务、商业使用条款、署名和缓存有效期，再把本地样例适配为统一 Weather 状态。上线前按 [`production-and-integrations.md`](../operations/production-and-integrations.md) 执行 Provider 故障、配额、费用和隐私验收。

## 本阶段明确不做

- 不申请或提交真实地图、天气、模型 Key，不调用商业 Provider。
- 不加入分享、共同编辑、社交、支付、订票或管理员功能。
- 不把模拟天气、示意地图或测试 fixture 描述成真实服务结果。
