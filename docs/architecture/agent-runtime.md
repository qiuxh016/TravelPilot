# TravelPilot Advisor Agent Runtime

`AgentRuntime` validates its execution limits and tool registry at construction: step, attempt and generated-token budgets must be non-negative integers; tool names must be non-empty and unique; retry limits must be non-negative integers; and timeouts must be positive finite numbers. Invalid runtime configuration fails immediately instead of silently shadowing a tool or producing a confusing later limit failure. A zero budget remains valid for intentionally disabled execution paths.

Status: the current Advisor supports bounded destination/place discovery, meal and lodging search, weather-aware preparation, routes, schedule drafts, existing-trip replanning handoff, and user-confirmed writes. The current authenticated local product-service suite passed 18/18 scenarios across 22 turns with a local model stub, Fake Maps and synthetic weather; all temporary accounts were deleted and no formal plan was written. The bounded DeepSeek product suite passed 16/16 scenarios across 20 turns, but this is not arbitrary-trip competence. The deterministic 40-case B1/B2/B3 comparison scored 20/40, 36/40 and 40/40 expected actions respectively; hard-invariant violations were 11, 1 and 0. Those scripted fixture results are not live-model quality evidence. Independent human ratings, a new held-out product-service comparison and broad user-utility evidence remain open. Production deployment, sustained quota/availability and external-pilot operations are deferred by scope.

Memory-related turns are read-only: the Agent may use only owner-authorized memories already loaded into its session context, and receives no memory-write tool. Saving or changing a memory remains a separate user-confirmed product action.

Place-intent extraction receives at most five active, confirmed soft travel preferences (160 characters each) in a structured input field. Hard limits are excluded from search hints and continue through deterministic draft-conflict checks. The extraction contract allows these soft preferences to influence only broad recommendation query categories; it cannot create a place action, schedule, date, pace change or approval. The complete live suite exercises bounded task extraction and routing; preference relevance and recommendation utility remain unmeasured.

## Current local implementation slice

Explicit in-trip fatigue, weather change, delay, venue closure, reservation change and temporary place-add requests now hand off to the existing event-replanning workspace when the selected trip has a saved plan. The Advisor emits `HANDOFF_TO_EVENT_REPLAN` with the event type and bounded prefill for explicitly stated weather or delay facts; it does not change session pace or generate an ordinary full-trip draft. The event page requires the user to enter uncertain timing/details, select a trip-scoped place, and provide confirmed opening hours for a new stop; the backend checks route/time feasibility and records a diagnostic instead of claiming an addition when no slot is verifiable. Every event-scoped preview/diff remains confirmation-gated. Focused Playwright covers desktop and Pixel 7 for all six event types, including a route-aware insertion. The handoff is still a navigation to the event workspace, not a single in-chat execution loop; an embedded preview/confirmation workbench remains future work.

The existing-trip schedule recommendation path now makes a bounded action choice between route lookup, the deterministic schedule builder and a focused user question. An `ASK_USER` action ends the turn with `NEEDS_USER_INPUT`; it does not run the planner. The model receives the user's bounded task text plus server-derived destination, dates, pace and fixed-stop count. After route lookup, it receives the verified matrix and can choose the next action. Server-owned coordinates are used, and matrix shape is checked before planning. A failed route call becomes an observation and the loop stops repeating the call; the itinerary can continue with a clearly labeled local estimate. A fresh matrix is reused on a later turn only when candidate IDs, context revision, evidence status and a ten-minute freshness window all match. The Advisor workspace renders the action source, decision summary, tool result, route provenance and the user's final save decision.

Candidate searches and dated forecast queries use a bounded read-only loop. The model receives only tools authorized for the current request: `search_places` accepts server-approved query terms and destination; `get_trip_weather` accepts no model-controlled fields and uses the selected trip's city and dates injected by the server. After observing verified results, it can select another approved search, ask one focused question, or finish. Arbitrary places, cities and forecast dates from model arguments are discarded. Provider failures and malformed results become observations for bounded recovery. Pending search/weather questions retain the original task type, goal and context revision so the next user answer can resume that goal; changing trip context invalidates the pending task.

Natural-language answer composition is a separate read-only step from place extraction. If extraction falls back because its structured output is invalid, the composer can still answer open-ended questions from the original message and supplied trip facts. It also receives at most six recent visible user/assistant messages from the same owner-scoped session, each truncated to 400 characters, to resolve follow-up references; hidden payloads and tool traces are omitted. Latest user input and verified trip facts take precedence. It cannot call tools or write trip data; specific places and live facts remain restricted to verified candidates/current-plan context. Scoped schedule, route, meal/lodging, weather and pending-question flows continue to own their turns and bypass generic composition. This is a fallback for extraction-format errors, not an outage fallback when the same model endpoint is unavailable.

Transport questions use a separate bounded read-only slice, `advisor/route_query.py`. The Agent can call `get_trip_route` with two IDs from the selected trip's saved places and a server-constrained driving, walking or public transit mode inferred from the user's request. Transit calls the [AMap Route Planning 2.0 API](https://lbs.amap.com/api/webservice/guide/api/newroute) and requires city codes preserved from AMap-verified place results; if either endpoint lacks a city code, the Advisor asks the user to refresh the saved places. Explicit route requests skip the separate generic place-extraction call and go directly to this action decision. The server resolves coordinates and names from the authorized trip snapshot, validates returned distance, duration, source, timestamps and geometry, and does not accept model-supplied coordinates. If endpoints are ambiguous it asks the user. Intercity rail and flights are clarified instead of silently returning an in-city estimate. Fake-provider responses are explicitly labeled simulated; verified-provider responses include route geometry and bounded transit segment labels for the UI without making a second route request. This supports point-to-point driving, walking and city-scoped transit lookup, not a general transport planner or multi-leg itinerary optimizer.

FIXED/RESERVED stops retain their date, time and status through draft confirmation. The draft endpoint rejects attempts to remove or move them. A resulting time or traffic conflict remains a blocker for confirmation.

The API router delegates session reads, trip-context snapshots, map tool adapters, schedule proposal orchestration, hard-limit checks, draft selection validation, confirmation guards and one-message turn orchestration to focused Advisor modules. Draft generation and confirmation are registered from `api/v1/advisor_drafts.py` and `api/v1/advisor_confirm.py`; the HTTP message handler is in `api/v1/advisor_messages.py` and delegates to `advisor/turn_service.py`. Destination discovery continuation and its result/session persistence live in `advisor/destination_service.py`; the turn service retains a compatibility adapter for injected map and session dependencies. The model can choose route lookup, the non-persistent schedule builder, approved map searches, dated weather lookup or a focused question. A shared output-token budget now accounts cumulatively for extraction, search, scheduling, route decisions and response composition, with exhausted budget leaving later phases at zero rather than granting each phase a fresh allowance. Pending schedule/search/weather questions, their original task and context revision are recorded in session context and assistant payload. Before resumption, the service refreshes the trip snapshot and rejects a pending task if its context revision changed. Opt-in personal memories are reloaded at the beginning of each turn; disabling memory or changing/deleting an active memory advances the context revision and clears stale session copies. Idempotency keys suppress duplicate message submissions; the Web client reuses a key after an uncertain network result when retrying the same message, preventing a committed action from running twice. Search/weather, route and schedule loops append state checkpoints to `advisor_run_events` in independent transactions. Verified route matrices, dated forecasts, map-search results and direct-route geometry can be restored after a same-key interruption when owner, session, task, context/query and provider scope plus freshness checks match. Weather snapshots omit the destination; search phrase and destination are hashed while only allowlisted provider place fields are stored. Direct-route snapshots omit names and are revalidated against the current saved-place set; trajectories remain account-scoped data. An owner- and task-scoped progress endpoint returns the newest bounded event window and filters events to the latest attempt per phase; raw user text and snapshots are not included in progress output. Session writes use PostgreSQL `FOR NO KEY UPDATE`, which serializes session writers while allowing checkpoint foreign-key inserts to complete. Intent classification and completeness checks still contain server-directed branches. The user-visible task taxonomy separates discovery, scheduling, meals, lodging, transport, weather, preparation, memories and general travel consultation, but labels do not imply that every task has a complete tool workflow. The product-grounded deterministic B1/B2/B3 comparison covers 40 schedule cases across 16 families; the 10-case open-consultation v2 set has live first-action scores of 10/10 for B2 and B3, without measuring multi-turn completion. The 16-case product suite is also complete on DeepSeek for its bounded API journeys. Preference relevance, held-out multi-turn task completion, independent blind review and broad user utility remain open.
The message-turn service maps loop terminal states through `advisor/task_state.py`: stale context, cancellation and user-wait states take precedence; a clean proposal is `PROPOSED`; failure/rejection/fallback/step-limit outcomes become `FAILED` or `PARTIAL` depending on whether usable results or a proposal exist; only a clean terminal outcome becomes `COMPLETED`. The main existing-trip search/weather, route and schedule stages now run through one observation-driven, dependency-aware turn executor. Intent classification and completeness checks still contain server-directed branches; destination discovery and specialized domain loops retain their own bounded runtimes, so this is not one universal planner for every travel task. Budget-prompt/cancel message writes, turn usage aggregation, and failed-turn usage retention are isolated in `advisor/turn_persistence.py`. `turn_service.py` keeps a thin adapter so its session reader remains injectable in route-level tests. Domain-stage dispatch and final response assembly still live in the coordinator and remain candidates for further decomposition.

Schedule proposals can include optional follow-ups for uncovered lunch/dinner periods and long gaps between visits. These are derived only from proposal rows matched to known candidates; unmatched data does not produce recommendations. Each option starts a separate scoped search, and the UI asks the user to regenerate and recheck the proposal before confirmation. If the same meal is also flagged by the trip completeness checklist, the checklist action is hidden while that meal appears in the draft follow-ups, avoiding two controls for the same search.

Read-only search dispatch supports bounded composite discovery: a user request for an indoor alternative plus forecast uses the discovery contract with map and weather tools, while an explicit meal or lodging request keeps that primary task and receives weather access only when weather was also requested and the trip has valid dates. The service appends forecast source, timestamp and grounded advice beside returned candidates. Point-to-point transport plus weather preserves the verified route and forecast in one answer; if only forecast dates are missing, the route result is still returned before asking for dates. This does not yet provide a general multi-intent planner; unrelated competing tasks still require explicit sequential task orchestration.

Message dispatch constructs an `AdvisorTurnPlan` (`apps/api/src/travelpilot_api/advisor/turn_plan.py`) as the source for primary task classification, authorized stages, dependencies and per-stage contexts. One `AdvisorTurnExecutor.execute_adaptive` call owns the complete planned search/weather, route and schedule graph for a message turn. After each runner completes, a result-integration callback updates the bounded current-turn state before the executor recomputes ready stages and asks the selector for the next action. For example, verified map candidates and weather observations are merged before the dependent schedule/route choice sees them. The selector receives only ready, server-authorized stages; every requested ready stage remains required, and failure to integrate a result marks that prerequisite failed so dependent actions remain blocked. The selector has no domain tool arguments and cannot commit data. Malformed output, timeout or insufficient output budget uses a stable server order. For requests with an idempotency key, choices are persisted as safe stage names, order and source with task/context scope; same-key recovery checks owner, session, task, context, decision observation and freshness. Historical choices are displayed but never applied to a retry without a new observation. Raw user text, model rationale and provider observations are not persisted in stage-choice records. Destination discovery and specialized domain loops still use their own constrained loops, so this is a unified main-turn stage driver rather than a universal action planner; complete cross-process reconstruction of arbitrary intermediate task state remains unfinished.


Progress checkpoints carry a random attempt reference. The progress API loads the newest bounded event window and filters events to the latest attempt per phase, preventing old failed attempts from appearing beside a retried run. The HTTP turn also emits an independent `TURN_STARTED` event, a 15-second liveness heartbeat and a terminal success/failure state. If the latest heartbeat is older than 60 seconds, progress reports `TURN_INTERRUPTED` with a same-message retry hint. The Web client stores only the idempotency key and a SHA-256 fingerprint in tab-scoped session storage, so re-entering the same message after a reload reuses the key without retaining raw text. Replaying the key returns a committed response or safely re-enters a rolled-back read-only task. The schedule/route composite separately persists its bounded stage order; `resolve_stage_order` reuses that choice after a same-key interruption and avoids repeating the selector call. Verified route matrices, weather forecasts, map search results and point-to-point routes have separate bounded snapshots. When a schedule retry restores its verified matrix, it continues directly to the deterministic draft builder rather than asking the model to select the same action again. Search/weather/route/destination discovery also persist an opaque hash reference to a pending approved tool action. Search and destination arguments are reconstructed from the current server-owned query/shortlist; route arguments are reconstructed from the current owner-scoped saved-place set. Actions are reused only if owner, session, task, context version, decision number, decision-observation digest and allowlist still match. Raw tool arguments and user/provider payloads are not stored. Other domain loops still do not share this exact-action recovery path; this is not a generic serialized runtime for arbitrary Agent actions.

Same-key stage retries additionally recover up to ten stage-selection records from the latest attempt. The checkpoint stores only allowlisted stage names, their selected order and the decision source. The workbench labels these records as recovered history; the executor never applies them as current decisions and instead rebuilds the current observation before selecting again. This preserves decision trace continuity without claiming that arbitrary intermediate outputs are restored. Goal text, model rationale and provider observations are excluded from this record.

## Original vertical slice (expanded incrementally)

The initial design targeted arranging locations already saved in an existing trip. The implementation has since expanded to bounded discovery, food/lodging, weather, route and preparation flows, while preserving the same principles: inspect scoped state, choose bounded actions, rely on verified evidence and return an editable proposal before formal writes.

Example task: “Plan a relaxed two-day visit from my saved places. I have a fixed appointment at 15:00 on day two; avoid unnecessary cross-city travel.” The Agent should use current trip state, preserve the appointment, query route evidence only when missing or stale, call the deterministic planner, verify the proposal, and ask for missing feasibility-critical information. The result is a draft with a constraint report and PlanDiff.

## Responsibility boundaries

| Component | Responsibility |
|---|---|
| `apps/api/.../api/v1/advisor.py` | HTTP auth, request validation, dependencies and response mapping |
| Advisor application services | Load trip-scoped context, run the interaction, manage state, create/revise drafts and map outcomes to responses |
| `travelpilot_core/agents/` | Reusable bounded Runtime, action contracts, loop, budget and verification primitives; do not duplicate this layer |

| Web Advisor workspace | Render conversation, visible action trace, evidence, draft, warnings, diff, pending questions and approval |

The existing-trip slice extraction is complete for message turns, drafts and confirmation persistence. Keep HTTP handlers focused on auth, request validation, dependencies and response mapping; preserve routes and public API contracts when extending other Advisor flows.

## Interaction state

The current implementation persists pending user questions and enough bounded task data to resume across user turns. It also persists state-only progress events across parent transaction rollback. Selected loops can restore narrowly scoped, validated evidence or approved action references after an idempotent retry (see the implementation notes above). This is not a general serialized runtime: arbitrary model decisions, observations and intermediate outputs cannot all be reconstructed after a process interruption. The following remains the target state for full cross-process crash-resume support:

- selected owner and trip IDs, supplied by the server after ownership checks;
- current trip and plan version snapshot;
- user goal, explicit constraints, known facts, unknown fields and source/freshness for each fact;
- current phase, bounded decision number, previously executed tool IDs and verified observation references;
- pending user question/consent request;
- draft version, validation report and diff;
- safe terminal/failure state and idempotency key.

Sensitive message text and raw provider payloads should not be copied into operational traces. Rebuild observations from authoritative trip/provider data where possible, and mark cached observations stale rather than silently reusing them.

## Decision and execution loop

The model emits one schema-validated decision at a time. Suggested kinds are `CALL_TOOL`, `ASK_USER`, `PROPOSE_DRAFT` and `FINISH`. Business-specific writes are not model actions.

```text
Observe current trip, plan, user goal and verified facts
  -> choose one allowed action
  -> validate action schema, tool allowlist, user/trip scope and budget
  -> execute tool through AgentRuntime
  -> verify ownership, schema, provenance, freshness and domain constraints
  -> append a safe observation and choose again
  -> return a draft, ask a focused question, or stop with a reason
```

The loop must be bounded by per-turn decisions, tool attempts, timeout, model output tokens, and per-user map/weather quotas. Retry only known transient failures. Invalid model actions, failed verification, stale data, hard-constraint violations and exhausted budgets stop the affected path; they do not trigger unbounded retries or silent removal of locations.

## Target registry for a broader planner

This is a design target for extending the current bounded domain loops; it is not a claim that every item below is already registered as a callable tool.

Expose only tools required by the vertical slice:

1. `get_trip_context`: trip-scoped dates, pace, budget, origin, saved places, current plan and version.
2. `get_distance_matrix` / route lookup: only when route evidence is absent or expired.
3. `get_place_details`: only when opening duration/hours materially affect feasibility and provider supports them.
4. `build_or_revise_draft`: call deterministic planning/replanning and return a proposal; no formal persistence.
5. `validate_draft`: return hard/soft constraints, provenance gaps, fixed-stop status and PlanDiff.

Private-message/media analysis and memory retrieval stay out of the current completed slice. Weather lookup is available only when the selected trip has a destination and both dates; otherwise the Agent asks the user to complete those fields. Broad destination search is not available unless the user has a selected destination or approved city; discovery without a city asks the user to narrow scope first. Tool arguments cannot set arbitrary `owner_id`, `trip_id`, SQL, URLs or provider credentials; the server injects authorized scope.

## Consent and persistence

- Read-only trip-scoped context and provider lookups may run automatically after the user selects a trip. Show the action and source in the workspace.
- The Agent may iterate on a session draft. Draft changes must be visible, versioned and undoable; they do not update the formal trip plan or wishlist.
- Formal Trip/Wishlist/Plan writes stay behind a separate explicit user confirmation. The server rechecks owner scope, draft version, hard constraints and idempotency at confirmation time.
- Deletion, social publication, sharing, or new use of private memories require their own explicit confirmation/setting and are outside the first slice.
- The model never receives a commit tool.

## Recovery and observability

Store state transitions and safe metadata: phase, selected action/tool, attempt count, duration, status/error category, token usage, provider usage, and draft/plan version. Do not store hidden chain-of-thought. A trace should explain observable evidence and the decision outcome, not expose private internal reasoning.

Recovery must distinguish a failed tool from a failed validation and a user-pending state. Replayed requests with the same idempotency key return the existing result; they must not repeat completed writes. If the underlying trip/plan version changes, invalidate the old draft and refresh context before proceeding.

## Acceptance checks

- Existing trip locations are loaded without asking the user to restate them.
- Route success, route failure, missing date, fixed appointment conflict, and infeasible schedule cause distinct expected actions.
- The deterministic planner enforces hard constraints; the Agent cannot override verifier results.
- No Trip/Wishlist/Plan mutation occurs before confirmation; stale versions and cross-user resources are rejected.
- Advisor session lookup filters by both session ID and authenticated owner ID; missing and foreign sessions return the same 404 response (`apps/api/tests/test_advisor_sessions.py`).
- A trace shows the sequence of actions, tools, verification outcomes and final state without secrets or hidden reasoning.
- The complete task can be demonstrated in one Advisor workspace on desktop and mobile.

## Synthetic evaluation boundary

`tests/evaluation/advisor_full_task_eval.py` runs the frozen 40-case/16-family v3 set through a replay of the historical fixed Advisor flow and two bounded-loop variants. All groups call the production itinerary planner against the same deterministic provider fixtures; the recorded comparison is reproducible from the repository. It is not a live-model decision-quality comparison. A separate two-case live smoke is recorded in `docs/evaluation/experiments.md` and its JSON artifact; it is too small to support broad quality claims. Further live-model evaluation requires a separately approved call budget.


`AdvisorTurnPlan` validates its dependency graph when created. Stage names must be unique; dependencies must refer to stages in the same plan, cannot be self-referential, and must form a DAG. This makes malformed cross-domain plans fail at the planning boundary rather than leaving the executor with no ready stage.


Turn dispatch resolves a dependency as complete only when its stage loop reports `SUCCEEDED`. A pending question, failed tool loop or rejected evidence does not unlock dependent schedule/route stages. POI search is a prerequisite only when the request asks to discover places; a dated weather lookup alone is independent from scheduling. Planned stages omitted because a prerequisite did not complete are reported as `BLOCKED_DEPENDENCY`, and task lifecycle resolution treats them as incomplete.

Stage ordering is coordinated through `advisor/turn_orchestration.py`: it invokes the bounded selector and applies the same owner/session/task/context/observation-bound checkpoint policy for both pre-search independent stages and post-search schedule/route stages. The post-search executor now runs one ready stage and then rebuilds its bounded observation before choosing again; this makes newly available weather/search evidence affect the next priority decision. Pending task recovery, cancellation and context-revision invalidation are resolved by the pure `advisor/turn_lifecycle.py` module; persistence and session refresh remain in the turn coordinator. Search, weather and direct-route loops can restore approved action references; the existing-trip schedule loop now uses the same policy for route lookup or deterministic non-persistent draft construction, bound to candidate and route-point scope. User-facing weather, route and schedule evidence summaries live in `advisor/turn_responses.py`. Stage report aggregation lives in `advisor/turn_reporting.py`; these modules do not execute tools or mutate trip state. `turn_service.py` remains the top-level turn coordinator and still contains domain dispatch, phase boundaries and response policy that should be split incrementally.

`advisor/stage_execution.py` now provides one `AdvisorTurnExecutor` instance per message turn. It retains stage outcomes, selection history and lifecycle sequence across the route-first, search/weather and post-search schedule/route execution boundaries, so retries within those boundaries cannot silently reset stage numbering or re-run a terminal stage. The executor normalizes each model-selected order against the server-authorized eligible set, retains every required stage and exposes the bounded decision history in the turn trace. Unexpected runner failures become bounded terminal traces; independent stages can continue and failed prerequisites do not unlock dependents. The executor state itself remains in process memory for the duration of the request. `turn_service.py` still constructs observations and invokes the selector at phase boundaries, while exact tool-action checkpoints remain owned by each domain loop; full-turn crash restoration and a single model decision loop across all task types are not implemented.

### Stage-order bypass audit (2026-10-20)

Repository call-site audit found one `execute_adaptive()` call, in `advisor/turn_service.py`; its runner registry contains only the request-authorized `ROUTE`, `SEARCH_WEATHER`, and `SCHEDULE` stages, and each selection is reconsidered after its outcome. No production caller uses `execute_ready_stage_queue()`. The only direct `AdvisorTurnExecutor.execute()` call outside that driver is `advisor/destination_service.py`, which submits exactly one bounded `SEARCH_WEATHER` stage to wrap free-city discovery in the shared lifecycle; it does not impose an order among multiple stages. Route, search/weather and schedule each retain their internal domain-specific constrained tool loop. No separate server-directed multi-stage ordering bypass was found in current call sites. This audit does not establish that future workflows are dynamically orchestrated: any new compound task must register its authorized stages with `execute_adaptive()` and test outcome-dependent reselection.

On a same-idempotency-key retry, `load_turn_stage_checkpoint()` may restore the previous sequence offset and identify a stage left at `STAGE_STARTED`, but only for the same owner, session, task hash and context revision within ten minutes. It never treats that stage as successful or skips it. The new response marks the retry, and its domain runner must revalidate or reconstruct evidence through the existing provider/action checkpoints. This is safe restart metadata, not full restoration of turn observations or outputs.

The Advisor workbench renders each recorded stage-order decision as a separate progress item with its source, summary and resulting stage order. Desktop Chromium and Pixel 7 acceptance assert that the model-selected order and completed route/schedule actions are visible. This shows the decision trace for supported itinerary tasks; it does not make unsupported tasks tool-capable or establish general model quality.


`AgentTaskContext` enforces disjoint `known_facts` and `missing_facts`; contradictory fact labels are rejected before a domain policy receives the task.


On an idempotent retry, the message API distinguishes a committed user message with a committed assistant response from a persisted user message with no response. The latter resumes the existing task while suppressing a duplicate user insert and removing that message from prior-turn context. If a later user message precedes any reply, the API rejects out-of-order replay rather than appending an old answer after newer conversation.

Assistant reply payloads now include `response_to_idempotency_key` for exact matching on new turns; legacy messages retain the adjacent-message compatibility check. Budget-control replies reuse an existing user message during recovery and carry the same response association.

### Recovery of completed intent extraction

When a message has an idempotency key and a configured model, the Advisor stores a short-lived extraction checkpoint after a successful extraction and before proceeding to later work. The checkpoint is scoped to owner, session, task key, and a digest of the task goal, bounded recent conversation, confirmed preference memories, context revision, output budget, model, and endpoint. It stores typed extraction fields and token usage; evidence text is represented as offsets into the already persisted user message. It does not persist a second copy of the raw user quote.

If the process exits later during reply composition, the same-key retry may reuse that checkpoint, restore the extraction token usage, and repeat only the unfinished response work. A successful response transaction consumes the checkpoint, and expired checkpoints are pruned when another checkpoint is written. A request interrupted while still in flight has no completed result to reuse and will be retried. A process can also die in the short interval after the provider response arrives but before the checkpoint transaction commits. Provider-side idempotency is not established, so either interruption can still repeat a billable request. This checkpoint covers intent extraction only; it is not a durable snapshot of arbitrary Agent decisions, provider observations, or side effects.
