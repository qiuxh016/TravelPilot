# TravelPilot 下一阶段计划

更新日期：2026-10-18  
计划范围：将现有旅行工具推进为可稳定试用的多用户产品，并把 AI 旅行顾问升级为能自主选择步骤、调用工具、校验结果并等待用户授权的 Agent。  
当前策略：保持单 Agent；暂不引入 Multi-Agent。Agentic 顾问成为下一阶段主线，现有确定性规划、地图、天气、记忆和最小改动重规划作为其可调用能力与验证层。

## 二、下一步执行顺序

### P0：完成当前版本的端到端验收

**目标：**先确认现有功能能从用户入口一路走通，并把页面/API/配置错误与真实服务故障区分开。

1. 固定本地启动方式与访问地址：确认 Web、API、数据库和 Worker 的实际端口及健康状态；启动时确认 API 读取的是预期 `.env`，不输出或截图泄露密钥。
2. 使用临时测试账户验证注册、邮箱验证、登录、退出和重新登录；检查用户进入工作台时不会长时间停留在“验证登录状态”。
3. 验收核心旅行路径：创建旅行 → 搜索并收藏地点 → 生成计划 → 查看天气和地图 → 记录现实事件并查看重排差异 → 管理旅行记忆。
4. 验收顾问保存路径：新建/选择会话 → 提供偏好或地点 → 检查核验状态与警告 → 修改草案 → 用户确认 → 检查 Trip、Wishlist、Plan 及新版本是否一致。
5. 验收账户路径：打开账户隐私页 → 添加/修改/删除偏好记忆 → 开关记忆使用 → 导出 JSON → 删除临时账户并确认关联数据清理。
6. 桌面与手机分别检查旅行概览、创建旅行、计划和账户页的首屏、空状态、加载/错误反馈、键盘焦点和破坏性操作提示；修复重复入口、无法区分的主次操作和移动端溢出。
7. 针对两个账户验证：列表不串数据；直接访问他人 Trip、Plan、顾问会话、记忆和分享资源不能读取或修改。

**验收标准：**以上核心路径至少在本地真实数据库和浏览器完整走通；失败提示说明可恢复的下一步；所有权测试通过；每个自动化测试账户都清理，不使用真实用户账户做破坏性验收。

### P1：完成真实天气与高德地图联调

**目标：**确认当前页面展示的是哪种数据、来自哪个 Provider、对应什么时间范围，并在服务不可用时如实降级。

1. **天气联调：**确认 Trip 目的地能被 Open-Meteo 地理编码正确匹配；选择预报窗口内和窗口外的日期各验证一次。页面区分有预报、部分日期覆盖、未覆盖、加载中和 Provider 失败，并显示来源、获取时间与许可署名。
2. **天气规则：**未来 16 天以外不生成模拟天气；手动 `WEATHER_CHANGE` 始终明确标为用户模拟事件；天气建议不自动覆盖已有计划，只有用户确认后才生成/保存重排版本。
3. **高德联调：**在实际运行 API 的进程中检查 `MAPS_PROVIDER=amap` 与服务端 `AMAP_API_KEY` 是否生效；验证搜索、详情、驾车时间、矩阵和静态地图，并记录成功状态而不记录 Key。
4. **失败场景：**分别验证无效 Key、超时、空结果和配额/上游错误；已保存的地点和行程不能因刷新失败消失；Fake Provider 只能用于明确标示的开发/演示场景，不得静默伪装成真实结果。
5. **路线表达：**已从高德驾车步骤解析真实道路 polyline，并把相邻行程地点的驾车路线几何传给高德静态地图绘制；没有取得完整道路几何时只显示地点，不再用直线冒充道路。地图说明同时提示路线和耗时可能因路况变化。

**验收标准：**保存一份真实联调记录，包含日期范围、Provider 状态、来源/更新时间、典型失败响应和页面展示；不保存密钥。地图/天气故障不会生成看起来像真实结果的演示数据。

### P2：基础模型调用闭环（已完成首版，Agentic 扩展见第六节）

**目标：**证明配置的模型能辅助理解与表达，但无法绕过地点核验、确定性规则和用户确认。

1. 从服务端加载模型配置；提供不回显密钥的“已配置/未配置/上游不可用”状态。前端不保存、不传递模型 API Key。
2. 在已知调用预算内，用少量人工选定场景验证正常响应、空/畸形结构、超时、错误 Key 和无 Key 回退；记录模型名、耗时、token/成本统计，不把个人对话写入普通日志。
3. 分别验证“用户明确说出地点”“目的地偏好探索”“修改已有计划”“约束缺失需追问”。模型提及的地点必须通过地图核验并由用户选择；无法核验时不得进入正式计划。
4. 用至少一组硬约束、一个 Provider 故障和一个已确认偏好冲突场景验证：排程硬约束由代码执行；记忆仅在启用时注入；模型失败不丢用户输入或旧计划。
5. 若真实请求显示模型目前只能抽取明确地点、无法可靠完成用户期望的目的地推荐，再单独设计推荐流程和评测集；不先把“可聊天”视为“能自主规划”。

**验收标准：**真实模型调用过程可观察、可限额、可回退；模型输出经过 Schema 校验；地点与计划只有经 Provider/规划器处理且由用户确认后才能写入；结果质量用固定案例记录，不以单次成功作为质量结论。

## 六、下一阶段：AI 旅行顾问 Agentic 化（2026-10-18）

### 目标

让顾问从“用户每轮下指令、系统按固定分支响应”升级为“用户描述目标，单 Agent 自主决定下一步、调用允许的工具、根据观察调整计划，并在需要用户决定或授权时暂停询问”。Agent 应能连续完成理解上下文、补足信息、检索和验证、构造候选方案、检查约束、解释差异的工作；不能把一条模型回复或意图分类称为完整 Agent。

保留现有确定性规划器、约束检查、PlanDiff 和用户确认写入作为执行底座。LLM 负责目标理解、下一步选择、必要追问和解释；地图/天气等 Provider 负责事实；代码负责权限、硬约束和持久化边界。

### 当前与目标的差距

| 领域 | 当前工作区/已有能力 | Agentic 目标 |
|---|---|---|
| 意图理解 | 提取地点、偏好和部分意图；若干常见需求由固定分支识别 | 解析目标、约束、已知事实、未知项及用户授权范围，结构化保留置信度和证据 |
| 下一步决策 | 搜索和排程主要由 API 固定流程决定 | 每次观察后，从服务端提供的有限 Action Schema 中选择调用工具、追问、给方案或结束；支持按结果改计划 |
| 工具调用 | 已有工具白名单、参数校验、超时/重试和受限 Agent Loop；顾问工具面仍较窄 | 顾问复用同一 Runtime 与 Verifier，支持地图、天气、旅行上下文、行程优化、草案检查等按需调用 |
| 旅行上下文 | 会话包含旅行/计划快照；消息入口开始刷新当前计划 | 每轮从所有者范围内读取最新旅行状态；持久化待办、已知条件、工具观察、草案版本和恢复点 |
| 行程操作 | 可生成排程草案并由用户确认保存；既有修改覆盖范围有限 | Agent 可自主反复改“会话草案”，验证路线/营业/节奏/预算约束，并总结最小改动；不直接提交正式 Plan |
| 交互与可观察性 | 对话、草案、工具行动标记刚开始连通 | 明确展示 Agent 当前步骤、工具依据、验证结果、待用户回答/授权内容、失败恢复和草案差异 |
| 效果证据 | 确定性评测和少量模型调用记录；模型评测样本有限 | 建立任务成功、约束、安全、追问质量、工具效率、成本和延迟的固定评测集与真实调用抽样流程 |

### 权限与同意分级

| 等级 | Agent 可做的事 | 用户确认方式 |
|---|---|---|
| 自动执行的只读步骤 | 读取当前用户主动选择的旅行上下文；检索地点；查路线/距离和天气；验证时间、营业窗口及旅行约束 | 无需每次打断；界面显示正在查询什么、结果来源和时间 |
| 会话内可撤销的草案操作 | 在当前会话新增/移除候选、调整建议时间、生成替代方案、维护未确认草案 | 可自动迭代；每次展示变更摘要，支持撤销/恢复。不得写入正式收藏或 Plan |
| 需要明确同意的敏感或有外部影响操作 | 将草案写入正式 Trip/Wishlist/Plan；删除收藏或旅行；分享照片/行程；首次启用记忆或扩大数据使用范围 | 在动作发生前展示影响范围、涉及数据和目标旅行；由用户单独点击确认。确认接口使用草案版本/一次性确认状态并保证幂等 |
| 不提供给 Agent 的能力 | 订票/订房/付款、联系商家、替用户发布动态、任意 URL/SQL/命令执行、访问其他用户数据、绕过硬约束 | 不进入工具注册表；后续要做须另立产品与安全设计 |

默认只把明确选择的当前旅行及该用户已开启使用的记忆作为上下文。切换旅行后显式刷新并展示新上下文；不能从其他会话或好友内容自动拼接信息。必要信息缺失时只问会改变可行性或偏好排序的问题；可先给部分方案时，应说明假设和未知项，而非用默认值伪装用户决定。

### 目标执行循环

```text
读取当前用户/旅行状态
  → 归纳目标、约束、已知与未知信息
  → 选择下一动作（工具调用 / 追问 / 生成草案 / 结束）
  → Runtime 校验权限与参数并执行
  → Verifier 核对工具结果、来源、约束与旅行归属
  → 把核验后的观察加入状态，再决定下一步
  → 形成草案和可读差异
  → 需要持久化时请求用户确认
  → 确认接口重新检查版本、权限和约束后提交
```

Agent 每个决定均为有限结构化 Action，模型不能自行生成新的工具、改变 allowlist、注入 owner_id/trip_id 或直接调用数据库。对不可验证结果、工具失败、计划不可行和模型低置信解析应停止相关动作，解释原因并给出可继续的选项；不循环重试、不静默删点。

### 工具面设计

工具按职责注册在服务端，参数由 schema 限定，用户/旅行范围由服务端注入：

1. **上下文读取：**读取当前旅行摘要、日期/预算/节奏/出发地、收藏地点、当前 Plan 及版本、用户允许使用的偏好记忆。只返回完成当前任务所需字段。
2. **地图检索：**按城市、类别或用户地点名搜索 POI；读取详情、坐标、地图评分/营业数据（Provider 有返回时）；所有候选携带来源、检索时间和核验状态。
3. **路线和天气：**按需获取地点间交通时间/道路路线几何及日期天气。缺失或过期数据显式标注，不让模型补造；同一轮复用结果，避免重复扣 Provider 额度。
4. **旅行方案：**调用确定性排程器、最小改动重规划器和约束验证器。Agent 可选择调用顺序和备选搜索策略，但不能更改硬约束结论。
5. **会话草案：**以版本化会话草案为工作区，Agent 可提出候选增删和时间调整；每次变更生成 PlanDiff/原因。该工具不触碰正式 Trip/Wishlist/Plan。
6. **正式提交：**不注册为模型可调用工具。只由前端确认动作触发独立 API；服务端重新验证草案仍有效、版本一致、旅行归属正确、硬约束通过，再幂等写入。

### 主实验问题与评测门槛

**主实验问题：**受约束 Agent 决策循环能否在动态旅行任务中，比固定顾问工作流提升端到端任务完成率，同时保持硬约束与用户授权安全？本轮只设一个主问题；天气重规划算法保留为次级独立评测，不把记忆优化、Skill 迁移或偏差审计并列包装成主创新。

| 对照组 | 系统 | 目的 |
|---|---|---|
| B1 | 当前固定顾问流程 | 任务完成、追问、约束与成本基线 |
| B2 | Agent Loop + Tools | 测量自主选择工具和行动的价值 |
| B3 | Agent Loop + Tools + Verifier + Recovery | 测量校验与恢复机制对可靠性的贡献 |

第 1 周固定 8–10 条任务建立 B1；之后每完成一个切片都用同一冻结任务回归；第 6–7 周扩至 30–50 条，覆盖故障和边界；第 8 周固定代码、模型、参数、Provider 模式和预算后完成对照。真实模型调用须先设定明确预算并使用受控账户，不能为追求分数反复调同一批题。

分开报告两层指标：

- **确定性规划层：**可行率、硬约束违规、预约保留率、路线成本、最小改动成本、无解判断准确性。该层结果不归因于 LLM Agent。
- **Agent 决策层：**端到端任务完成率、有效追问率、工具选择/顺序合理率、Decision Adaptation Rate、工具失败恢复率、重复调用率、token/Provider 成本与延迟。

Decision Adaptation Rate 使用同一任务的预设状态变体评分：地图成功时采用验证路线；地图失败时停止不可验证规划或说明降级；预约冲突时保留预约并调整其他地点或追问；时间/预算不足时追问或报告无可行方案。期望动作须在运行前固定。

Skills 作为辅助项：主实验固定 Skill 开关或固定版本，避免混淆 Agent Loop 的贡献；主实验完成后最多做一项轻量业务消融（例如雨天 Skill 是否减少无效工具调用），不建设 Skill 自学习或迁移系统。

- **任务质量：**任务完成率、有效追问率（只追问影响可行性/排序的信息）、地点证据匹配率、草案被接受率、用户修改轮数；按探索、已有旅行、修改、天气事件分层统计。
- **计划质量：**硬约束违规数必须为 0；预约/固定节点保留率；地点覆盖率；路线时间、空档与每日节奏；相对基线的变更节点数和加权 change cost；不可行时正确拒绝率。
- **Agent 执行：**Action Schema 通过率、Verifier 拒绝率、每任务工具次数、重复搜索率、恢复成功率、步骤上限终止率、端到端延迟、模型输入/输出 token 和地图/天气调用成本。
- **授权与隔离：**未确认正式写入数必须为 0；越权工具调用成功数必须为 0；确认版本冲突拒绝正确率 100%；每个工具都验证 owner scope。所有用户确认之外的草案更新须可撤销。
- **灰度条件：**先 Fake Provider + 确定性模型输出覆盖状态机；随后用固定测试账户及明确预算做真实模型/Provider 验收；最后邀请少数用户。离线结果、模拟结果和真实服务结果分开呈现；小样本只报告观察值，不包装成普遍质量提升。
